# 前端“越轨”行为分析

日期：2026-08-29
范围：`athena-gui` → Tauri bridge → Rust commands → Python GUI gateway → `ResearchRuntime` / Supervisor。

## 结论

这份探索的核心判断成立，但应将“前端越轨”准确表述为：**前端编排并触发了一条独立于 Supervisor 的、由 Python 后端执行的任务理解链路。**

浏览器没有直接调用模型、没有直接读写 `.athena/`、也没有直接修改 `state.json` 或研究树。因此问题不是客户端绕过后端的技术越权，而是任务理解的流程所有权分裂：同一条用户任务会分别进入 `parse_intent` 和 Supervisor 的任务理解回合，二者没有共同的权威结果和生命周期。

## 已证实的调用链

新任务提交时，`usePipeline.sendPrompt()` 会在不等待的情况下并行执行两条链路：

```text
用户输入
  ├─ void sendMessage(content)
  │    └─ RPC parse_intent
  │         └─ GuiService.parse_intent
  │              └─ 独立 LLM 澄清循环 / heuristic fallback
  │              └─ 写 TASK_CLARIFICATION.md 与 handoff_refs
  │
  └─ await startRun(content)
       └─ RPC start_search
            └─ ResearchRuntime.start_task
                 └─ maybe_run_task_understanding
                      └─ Supervisor turn
                           └─ record_task_understanding / configure_kaggle
```

证据：

- `athena-gui/src/hooks/usePipeline.ts:476-503`：`sendMessage(content)` 以 `void` 后台启动，随后调用 `startRun(content)`。
- `athena-gui/src/lib/tauri-bridge.ts:140-146`：`sendMessage` 映射到 `parse_intent`，`startSearch` 映射到 `start_search`。
- `athena-gui/src-tauri/src/commands/chat.rs:7-12`：Rust `send_message` 直接调用 Python RPC `parse_intent`。
- `src/gui_gateway/handler.py:29-40,270-275`：`parse_intent` 与 `start_search` 是两个公开且独立的网关入口。
- `src/athena/gui/service.py:70-129,167-173`：`parse_intent` 自己调用 LLM、等待澄清、持久化 handoff；`start_search` 只转交给 `runtime.start_task`。
- `src/athena/research/runtime/control.py:58-94,117-124`：启动后仍会执行 Supervisor 任务理解回合。

因此，“后端不知道前端已经理解过”并不准确。实际是后端的同一运行时知道原始消息并记录了一个 handoff，但 **Supervisor 不以该 handoff 作为任务理解的权威输入或完成标记**；它仍会运行自己的理解回合并写入 `state.task_understanding`。

## 对各项判断的评估

### 1. 独立 `parse_intent` 链路是最主要的问题

成立，且这是架构问题的核心。

`GuiService.parse_intent()` 不只是展示层解析：它持久化用户消息、执行自己的 LLM 澄清循环，并写 `handoff_refs["task_clarification"]`。与此同时，Supervisor 在 `maybe_run_task_understanding()` 中执行另一轮理解，并通过 `record_task_understanding()` 写 `state.task_understanding`。两条链路使用不同 prompt、不同完成条件、不同状态载体。

这会产生三类不一致：

- 重复提问或互相矛盾的任务理解；
- `TASK_CLARIFICATION.md` 与 `state.task_understanding` 的字段、时间点和结论不一致；
- `parse_intent` 异步完成的时机不受 Supervisor 生命周期约束，可能在运行已经推进后才覆盖 `handoff_refs["task_clarification"]`。

### 2. 前端决定“新任务还是 Supervisor 指导”

成立，但应定性为**客户端路由策略**，而不是浏览器独立完成业务理解。

`usePipeline.ts:441-473` 用 `viewModel.status`、本地 `runStarted` ref、plans、搜索次数和最新实验等 UI 投影来判断文本的去向：运行中时调用 `sendControl`，否则按新任务处理并触发启动。这意味着输入语义的分流不是由后端权威状态或一个显式会话模式决定的。

代码为避免首帧旧状态加入了多个补偿条件，说明作者已意识到该问题；但这仍然是易碎的状态推断。前端状态延迟、事件遗漏、恢复会话或并发点击，都可能改变同一句文本进入的后端入口。

### 3. 前端乐观置为“运行中”

事实成立，但严重性低于前两项。

`startRun()` 在 `startSearch()` 返回前设置 `phase: "PREPARE"` 和 `status: "running"`（`usePipeline.ts:364-385`），失败后将状态改为 `error` 并重置 `runStarted`。这没有写入权威运行时状态，因此不是单独的职责越界。

它之所以值得修复，是因为同一份乐观本地状态参与了第 2 项的输入路由；在 RPC 未确认或确认失败的窗口内，UI 可能把下一条文本解释成运行时指导。应把运行状态与输入路由都改为以后端状态事件或明确的会话命令为准。

### 4. 实验管理写操作绕过 Supervisor

事实成立，是否“越权”取决于产品政策。

前端 `ExperimentManager` 可调用 `experiment_transition` 与 `experiment_set_sota`；Python `GuiService` 直接修改 `ResearchTree` 并 `save_tree()`（`src/athena/gui/service.py:286-295`）。底层仍有状态转移和 SOTA 合法性校验，且现有 GUI 设计明确把这些作为“写操作显式暴露”的人工管理能力（`docs/athena-gui-design.md:35-40,252-262`）。

所以它不是未设计的事故。但若架构原则是“Supervisor 是 `ResearchTree` / `ResearchState` 的唯一写者”，这里确实违反单写者原则；应明确选择：

- 保留为有审计记录、运行中禁用或需要确认的人工覆盖能力；或
- 删除这两个写 RPC，改由 Supervisor 接收显式人工指令后执行。

### 5. 未发现浏览器直接越权

成立。当前调用均经 Tauri、Rust bridge 和 Python RPC 到达后端。`parse_intent` 的 LLM 调用实际发生在 `src/athena/gui/service.py`，不是 React 代码中。

## 对“简单回写后跳过 Supervisor”的评估

不建议这样做，探索中的反对理由正确。

`maybe_run_task_understanding()` 只要发现 `state.task_understanding` 非空就直接跳过（`src/athena/research/runtime/control.py:63-71`）。但 Supervisor 的任务理解回合还拥有：

- `configure_kaggle`：保存本次运行的 Kaggle 启用和下载决策；
- `record_task_understanding`：将理解结果以 Supervisor 状态模型持久化；
- 任务理解回合的后续工具决策和运行时事件语义。

而 `parse_intent` 的 `TaskUnderstanding` 只包含标题、数据集、目标、任务类型、指标、方向和评估计划，不包含 Kaggle 决策，也没有通过 Supervisor action 写入状态。因此将其直接写入 `state.task_understanding` 会把“已有理解”错误地当作“Supervisor 初始化完成”，可能跳过必要的配置。

## 推荐目标架构

将 Supervisor 设为唯一的任务理解编排者，前端只承担输入、状态展示和人机问答呈现。

```text
前端提交新任务
  └─ start_search(task)
       └─ ResearchRuntime.start_task
            └─ Supervisor task-understanding workflow
                 ├─ 请求 human input（human_pending / human_reply）
                 ├─ configure_kaggle
                 ├─ record_task_understanding
                 └─ 生成并登记 TASK_CLARIFICATION.md（若保留）
                      └─ 前端消费 state / output 事件并渲染
```

推荐的收敛步骤：

1. 前端新任务仅调用 `start_search`；删除 `sendPrompt()` 中 `sendMessage()` 的并行调用与 `awaitingIntent` 对该入口的依赖。
2. 让前端从后端 `state.task_understanding` 和输出事件渲染预览，而不是消费 `parse_intent` 返回值。
3. 将多轮澄清及 `TASK_CLARIFICATION.md` 的生成迁移到 Supervisor 的任务理解流程，继续复用既有 `request_user_input`、`human_pending`、`human_reply` 和 `HumanRequestDialog`。
4. 删除 `parse_intent` 的公开协议：同时移除 TypeScript bridge、Rust `send_message` 适配、`SUPPORTED_METHODS`、网关 dispatch 与 `GuiService.parse_intent`；若必须短期兼容旧客户端，将它降级为调用同一 Supervisor 工作流的薄包装，不能保留独立 LLM loop。
5. 将“新任务 / 运行时指导”的路由收回后端，或改成 UI 明确的、新任务和发送指导两个命令，避免从本地投影状态推断用户语义。
6. 就实验管理写入作出明确架构决策，并以测试锁定：人工覆盖的权限、运行中行为、审计和与 Supervisor 的并发规则。

## 迁移风险与验收点

- 不要用前置澄清结果直接填充 `state.task_understanding`，除非同一 Supervisor 工作流也完成 Kaggle 和其他初始化决策。
- 不要仅删前端调用而保留 `parse_intent`；公开 RPC 仍会让旧客户端或后续代码重新引入第二条链路。
- 保留任务理解的用户可见进度和取消能力；当前 `start_search` 已将生命周期放入可取消的后台任务。
- 为迁移新增端到端测试：一次新任务只产生一次任务理解、一组澄清问题和一份最终 handoff；Kaggle 任务仍完成配置；运行中指导永远进入 Supervisor；未运行时指导不会被误作新任务。

## 最终判断

探索结果在方向上是合理的，尤其是“统一到 Supervisor、前端只呈现后端权威状态”的建议。需要修正的措辞是：这不是前端直接进行 LLM 推理或文件写入，而是前端选择并并行触发了一个后端 `parse_intent` 副流程。

最需要避免的修复是把副流程的结果简单回填为 `state.task_understanding` 并跳过 Supervisor。正确的收敛方式是把澄清、任务理解、Kaggle 决策和 handoff 生成放入同一个 Supervisor 工作流，再逐层移除旧的 `parse_intent` 入口。
