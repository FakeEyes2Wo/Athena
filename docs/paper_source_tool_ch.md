# Paper Source Tool

面向读者：复核本模块设计与取舍的人，以及开发上下游协同模块（AcademicSurvey、RAG 摄取）
的人。上游需要交出什么、字段怎么填，见[上游契约](paper_source_upstream_contract_ch.md)；
下游怎么消费产物，见 [paper_markdown](paper_markdown_tool_ch.md)。

## 定位

paper_source 把「一批被判定为相关的论文标识符」变成「一批版本固定、经过字节校验的正文
文件」，并直接产出 paper_markdown 可以执行的转换请求。

它填补的正是 paper_markdown 明确声明不负责的那一段：网络检索、arXiv/DOI 解析与下载。
工具注册名为 `paper_fetch`。

### 为什么值得单独一层

检索阶段拿到的是「看到过的东西」——跨命名空间且写法不一的 id、可能过时的标题、可能失效
的链接；转换阶段需要的是「确定的字节」——一个已知格式、已知版本、内容可寻址的文件。这
两者之间有一段真实的工作量：版本解析、通道回退、字节判定、请求预算控制。把它塞进检索侧
会让检索模块背上限流与合规责任；塞进转换侧会让一个纯计算模块变成需要联网的模块，单元
测试再也不能离线跑。所以它是独立的一层。

### 协作边界

| 模块 | 责任 |
| --- | --- |
| AcademicSurvey（SPAR + GEPA） | 检索论文、判定相关性、给出标识符线索与候选下载链接 |
| Athena 运行时 | 创建共享 ArtifactStore、注册工具、注入联系邮箱与可选 API key |
| **Paper Source Tool** | **解析版本、选择通道、下载并校验字节、落盘并生成转换请求** |
| Paper Markdown Tool | 消费转换请求，解析结构并产出 PaperContent |
| RAG 摄取模块 | 以 `paper_key` 为命名空间建立索引 |

本工具不负责：

- 判断论文是否相关、是否值得读——那是上游的职责；
- 跨检索通道的去重与元数据融合——上游在合并检索结果时已经做过；
- 解析 TeX/PDF 的正文结构；
- 向外分发下载到的 e-print（见「许可与合规」）。

## 六条设计原则

复核时最值得质疑的就是这六条，因此每条都附上理由。

**一、arXiv 优先。** 能拿到 TeX 源码的通道排在所有 PDF 通道之前。TeX 里公式、标签、
交叉引用、图表标题都是结构化的，PDF 则需要从版式反推这些结构，而版式还原是 paper_markdown
质量损失的主要来源。对一个以 AI4S 文献为主的语料库来说，arXiv 覆盖了绝大部分目标论文，
这个偏好的实际收益很高。

**二、版本固定。** 默认拒绝无版本下载。`2501.10120` 会随作者更新指向不同正文，
`2501.10120v2` 不会。RAG 索引一旦建立就要能追溯到确切的字节；如果同一个 key 在两次运行
中对应不同正文，引用定位、增量更新和结果复现全部失效。放宽这一条需要显式打开策略开关，
并且会收到一条警告诊断。

**三、身份先于网络。** `paper_key` 在发出任何 HTTP 请求之前就由上游给的身份算定，之后
无论解析补全出什么都不再改动。这一条看起来保守，但反面是真实的故障：如果 key 会随「这次
有没有成功补到 DOI」而变，同一篇论文会在语料库里出现两份互不相识的副本。解析阶段拿到的
DOI 只会补进身份字段和元数据，不会移动 key。

**四、字节自证。** 只信任魔数，不信任 URL 后缀、`Content-Type`，也不信任上游的开放获取
声明。理由见下文「字节判定」一节——这不是防御性冗余，是一个已经存在的静默错误的唯一防线。

**五、请求预算显式。** 元数据批量解析一次覆盖 60 篇；按篇计费的只有下载阶段；重跑走本地
定位符缓存。结果里 `http_requests` 汇报本批实际发出的请求数，可以直接核对预算。

**六、显式降级。** 每一次跳过、退化和拒绝都写成一条带稳定代码的诊断，不静默丢弃。上游
给错链接、arXiv 没有源码、许可缺失——这些都是上游或运维需要知道的事实，藏起来只会让问题
在 RAG 检索质量下降时才暴露，那时已经很难追查。

## 处理流程

```text
上游检索结果
    │
    ▼
① 按 max_papers 截断，保留上游排序
    │
    ▼
② 批量解析 arXiv 版本与元数据（每 60 篇 1 次请求）
    │
    ▼
③ 逐篇取源：arXiv 源码 → arXiv PDF → 开放获取 PDF（唯一按篇计费的阶段）
    │
    ▼
④ 魔数判定 → 落盘 → 生成转换请求
    │
    ▼
逐篇结果 + 每篇一个转换请求引用 → paper_markdown
```

阶段顺序是刻意的。先批量解析再逐篇下载，是因为 arXiv 的元数据端点按 id 列表计费，一次
最多 60 个；逐篇调用会把请求预算放大两个数量级。魔数判定放在最后而不是下载时，是因为
它需要完整字节。

## 通道优先级

按固定顺序尝试，第一个产出**可用字节**的通道胜出：

1. arXiv 源码端点（`/src/{id}v{n}`）——策略不是纯 PDF 偏好时；
2. arXiv PDF 端点（`/pdf/{id}v{n}`）——源码不可用时的退化；
3. 上游给的开放获取 / 出版方 PDF 链接，按输入顺序；
4. OpenAlex 记录里的开放获取 PDF 链接；
5. OpenAlex 计费内容端点——仅当策略允许**且**已配置 API key。

第 3、4 步合并成同一个候选队列，**整个队列只尝试前 3 个**，避免一篇取不到的论文吃掉整批
的请求预算。进入非 arXiv 阶段前会先查一次 OpenAlex 记录，用于反推可能存在的 arXiv id 和
开放获取链接——不少论文上游只给了 DOI，但其实有 arXiv 版本。

第 3 步的线索来自 `PaperRef.hints`。`paper_scout` 会把检索阶段顺带拿到的
`openAccessPdf` 链接写进去（`kind="oa_pdf"`），因此常见情况下第一个候选就能命中，省掉第 4
步的 OpenAlex 解析，也避开了 `best_oa_location` 指向第三方镜像的已知问题。上限 3 个候选保证
线索给错时仍会试到 OpenAlex 那条，不存在挤占。线索不是权威，字节照样要过魔数判定。

第 5 步默认关闭。OpenAlex 的元数据 API 免费，但内容端点按额度计费且必须持有 API key；
策略允许而 key 缺失时只记一条诊断，不发出注定失败的请求。

## 字节判定：为什么不可省

下载到的每一段字节都要过魔数判定，只承认四种结果：PDF、zip、gzip（tar.gz 或单文件）、
裸 TeX 正文。其余一律判为无法识别，并使该通道失败。

这一步是必需的，因为有一个具体的静默错误：**arXiv 的源码端点对「只投了 PDF」的论文会
直接返回 PDF 字节**，而 paper_markdown 的自动解包在识别不出归档格式时会把任意字节整体
当作 `main.tex` 处理，不抛异常。两者相接的结果是一篇论文静默变成一段乱码正文，进了 RAG
之后无法追查——检索出来的是乱码，但没有任何地方报错。

判定为 PDF 的源码响应会被改路到 PDF 字段，并记一条信息级诊断说明该投稿没有 TeX 源码。

同理不信任 `Content-Type`：出版方站点常把 HTML 拦截页标成 `application/pdf`。

### 安全边界

上游线索 URL 是不可信输入，而底层 HTTP 库支持 `file://`。取源时只放行 `http` 与 `https`，
其余记一条警告诊断后跳过。**不在候选收集阶段静默过滤**——否则上游永远看不到自己给错了
链接，这正是原则六要避免的情况。

## 输出契约

结果对象（schema 1.0）包含三部分：逐篇记录、批次统计、批级诊断。

### 逐篇记录

按输入顺序一一对应，通过 `ref_index` 可以直接对回上游的条目。每条给出：

| 字段 | 含义 |
| --- | --- |
| `paper_key` | RAG 命名空间键，与输入身份算出的完全一致 |
| `identity` | 补全后的身份（可能比输入多了 DOI） |
| `status` | `fetched` / `skipped` / `failed` |
| `channel` | 实际产出字节的通道 |
| `source_locator` | 精确溯源定位符，如 `arxiv:2501.10120v2/src` |
| `version` / `version_pinned` | 解析出的版本，以及下载 URL 是否真的带了版本 |
| `cache_hit` | 字节是否来自本地定位符缓存 |
| `tex_source_ref` / `tex_source_format` | TeX 包引用与魔数判定出的格式 |
| `pdf_ref` | PDF 引用 |
| `license` | 来源通道记录的许可串 |
| `metadata` | 写入转换请求的元数据 |
| `conversion_request_ref` | 可直接交给 paper_markdown 的请求引用 |
| `diagnostics` | 本篇的取源阶段事实 |

`status` 的判定规则是三分的，不要混淆：拿到字节是 `fetched`；试过但所有通道都失败是
`failed`；**被策略拒绝而根本没发请求**是 `skipped`。区分后两者是有意义的——`failed` 说明
数据源有问题，`skipped` 说明配置有问题，处理方式完全不同。

### 批次统计

汇报 `requested`（上游给了几篇）、`accepted`（截断后实际尝试几篇）、
`fetched` / `skipped` / `failed`、`cache_hits`、`http_requests`、`tex_sources`、
`pdf_sources`。

其中 `http_requests` 是本批实际发出的 GET 次数，含批量元数据查询，用于核对请求预算是否
符合预期。`tex_sources` 与 `pdf_sources` 的比例是语料质量的先行指标：PDF 占比偏高意味着
后续 paper_markdown 的结构还原压力更大。

### 诊断码

「责任」列指出这条诊断出现时该由谁处理。

| 代码 | 级别 | 含义 | 责任 |
| --- | --- | --- | --- |
| `paper_source.max_papers_truncated` | warning | 批次超过上限，尾部被丢弃 | 上游批次划分 |
| `paper_source.arxiv_lookup_failed` | error | 批量元数据查询失败 | 运维 / 数据源 |
| `paper_source.title_mismatch` | warning | 上游标题与解析出的标题相似度低于 0.75 | 上游元数据 |
| `paper_source.version_unresolved` | error | 版本未解析且不允许无版本下载 | 数据源 / 策略 |
| `paper_source.unpinned_version` | warning | 正在无版本下载，正文可能随时间变化 | 策略配置 |
| `paper_source.arxiv_source_unavailable` | warning | 源码端点不可用，已退到 PDF | 无需处理 |
| `paper_source.non_arxiv_channel_disabled` | info | 策略禁止非 arXiv 通道 | 策略配置 |
| `paper_source.openalex_lookup_failed` | info | OpenAlex 无可用记录 | 无需处理 |
| `paper_source.paid_content_unavailable` | info | 允许计费端点但未配置 key | 运维 |
| `paper_source.http_error` | warning | 通道返回非 2xx | 上游链接 / 数据源 |
| `paper_source.url_scheme_rejected` | warning | 线索 URL 协议不在白名单内 | 上游链接 |
| `paper_source.transport_encoded` | warning | 明确要求不压缩仍被压缩传输 | 运维（代理） |
| `paper_source.payload_not_recognized` | error | 字节既不是 TeX 包也不是 PDF | 上游链接 / 数据源 |
| `paper_source.pdf_only_submission` | info | 该篇 arXiv 上没有 TeX 源码 | 无需处理 |
| `paper_source.no_channel_available` | error | 没有任何通道可尝试 | 上游身份 / 策略 |
| `paper_source.transport_failed` | warning / error | 主机不可达：DNS、TLS 或超时 | 上游链接 / 网络 |

### 传输层失败必须降级，不能上抛

`HttpTransportError` 覆盖 DNS、TLS 握手与读取超时——它和"返回了非 2xx"是两回事，后者有
response，前者没有。这类异常**在任何一层都不允许逃出取源阶段**：

| 位置 | 失败时 |
| --- | --- |
| `_fetch_url` | 记 warning，继续试候选队列里的下一个 |
| `_fetch_one` | 记 error，这一篇标记 `failed`，批次继续 |
| `_resolve_versions` | 记 error，退回空解析，各篇按未钉版本继续 |

理由是成本结构：取源是唯一按篇计费的阶段，跑到第 12 篇崩掉等于前 11 篇的下载全部白花。
真机上出现过：一条 `doi.org` 线索 TLS 握手超时，异常一路逃到调用方，打断了 50 篇的全程。
线索 URL 来自检索后端，域名完全不可控，50 篇的批次里出现一个不可达主机是常态而非意外。

## 请求预算与限流

arXiv 的使用条款要求**每 3 秒不超过 1 次请求，且同一时刻只保持一个连接**。关键在于这个
限额约束的是整个服务，而不是某一个主机名——元数据、OAI-PMH 和 e-print 分别位于三个子域。

因此限流按**服务**分桶，不按主机名：三个 arXiv 子域收敛成同一份配额，每个桶串行执行并
预留时隙。这一层不能按主机分——取源流程恰好会依次访问这三个子域，按主机分桶会让实际
速率正好变成限额的三倍。OpenAlex 单独成桶，不会被 arXiv 的节奏拖慢。429 与 5xx 走指数
退避加抖动，并优先采信 `Retry-After`。

这个缺陷是真实网络验收暴露的，单元测试抓不到：假传输没有墙钟成本，看不出三个子域各拿了
一份预算。

单批 N 篇（全部为 arXiv、默认策略）的请求数为 **⌈N/60⌉ + N**：一次批量元数据加每篇一次
下载。开启许可获取会变成 **⌈N/60⌉ + 2N**，因为 OAI-PMH 每次只能取一篇。

重跑同一批语料时，定位符缓存（以 `arxiv:2501.10120v2/src` 这样的稳定定位符为键）让命中的
论文完全不发下载请求。内容寻址存储能去重字节，但去重不了 HTTP 请求，所以这一层缓存是必要
的。缓存条目在返回前会校验字节仍在存储中，否则降级为未命中重新下载，而不是交出一个悬空
引用。

所有请求都声明不接受传输压缩，保证下载字节与服务端负载逐字节一致——否则内容寻址就失去
意义（同一份内容会因代理是否压缩而得到不同的哈希）。

HTTP 层只用标准库，不引入新依赖：在「1 请求 / 3 秒、单连接」的节奏下，连接池与 HTTP/2
没有任何收益。

## 许可与合规

- arXiv 元数据为 CC0；正文 e-print 的许可逐篇不同，开启许可获取可取回原始许可串。
- arXiv 使用条款**禁止**把下载到的 e-print 从自有服务器再分发。落在本地存储中供内部
  RAG 使用属于合规范围，对外提供下载不属于。这一条约束的是部署方式，不是本模块的代码。
- OpenAlex 元数据 API 免费；内容端点按额度计费且必须持有 API key，因此默认关闭。
- 请求都带联系邮箱标识（由运行时注入），用于 arXiv 与 OpenAlex 的礼貌池。

## 验收状态

单元测试 33 个用例，全部不触网：标识符归一与 `paper_key` 稳定性、元数据与 OAI-PMH 解析、
四类魔数判定、限流分桶与子域共享预算、退避策略、通道选择与诊断、缓存重跑、协议白名单，
以及工具注册与生命周期事件。

真实网络验收覆盖三种 id 形态（新式 id、arXiv 自铸 DOI、旧式带斜杠 id）：

| 验证项 | 结果 |
| --- | --- |
| 字节同一性 | PaSa 源码包 sha256 与本地参考包逐字节一致 |
| 版本固定 | 三种 id 形态全部固定到具体版本（v2 / v1 / v3） |
| key 稳定性 | 旧式 id 补到了出版商 DOI，`paper_key` 未移动 |
| 请求节奏 | 冷启动 7 次请求 18.6 秒，符合 3 秒节奏 |
| 缓存 | 重跑降到 4 次请求、0 次下载 |
| 端到端 | 转换请求直接交给 paper_markdown，产出 97 个 chunk 与 23 个视觉对象 |

基线值：PaSa（arXiv:2501.10120）解析为 v2，源码包 sha256 为
`4ca56e1a2bbfba8cc16fc69dd174cc8d4c3bdcbc3313cad672455cf5e02ce9c4`。

## 已知限制

- 只有 arXiv 通道能拿到 TeX；其余通道最好情况也只是 PDF。
- 非 arXiv 论文没有可固定的版本概念，`version_pinned` 恒为假。
- 上游 PDF 线索与 OpenAlex 链接合起来最多尝试 3 个，超出部分不会被访问，也不单独记录。
- `arxiv_abs` 类型的线索目前不参与下载候选队列：有 arXiv id 就已经能定位，摘要页本身
  不含正文。
- OpenAlex 只用于反查链接与元数据，不作为正文来源。
- 定位符缓存是本地 JSON，不做跨进程加锁；多进程同时取源可能重复下载，但不会损坏数据。
- 标题交叉校验用的是字符级相似度，对同一篇论文的中英文标题会误报——目前语料全为英文，
  暂不构成问题。
