# Paper RAG Tool

`paper_rag` 是 `paper_markdown` 的下游检索层，把若干篇已转换的论文构建成语料，并向模型
暴露两类接口：**检索**（关键词、语义）按内容找入口，**遍历**（图文互链、引用、章节）沿
语料里已有的类型化边走一步，再加上整篇读取。

## 定位

`paper_source` 取源、`paper_markdown` 转换、`paper_rag` 检索，三层各自只做一件事。

Agent loop 不在本模块内实现——Athena 的 `core/agent` 已经是一个带工具调用的 ReAct 循环，
A-RAG 论文的贡献本就在"给模型什么样的检索接口"，而不在循环本身。本模块只提供接口。

### 协作边界

- 上游契约是 `PaperContent.load_retrieval_units()` 返回的 `RetrievalUnit`，不是
  `PaperChunk`。选它有两个理由：模块只依赖一个上游契约；`interpretation_status` 为
  `unavailable` 的视觉单元由上游自动排除，本模块不需要理解视觉策略。
- 不重新切分 chunk。上游的结构化切分不会从元素中间截断，重切只会丢掉 locator 溯源，
  而两者的粒度本就在同一量级。
- 建索引是库函数 `build_corpus_index`，不是工具。编码有真金白银的成本，不能让模型自己
  决定何时触发。

## 索引构建

语料索引拆成两个 artifact：`PaperCorpusIndex` 本体与句向量。关键词检索和整篇读取永远不
需要加载向量，拆开后这两条路径不必为语义检索的体积买单。

句子不存文本，只存指向父 chunk 正文的字符区间（`CorpusSentence.char_start/char_end`），
因此不存在正文的第二份副本，chunk 全文与句子视图永远一致。

### 结构感知切句

切句分三步：先按行切分，让 Markdown 表格行各自成为独立单元；跨行的展示公式块
（`$$ ... $$` 与 `\[ ... \]`）整块作为一个单元；再在行内按句末标点切分，跳过缩写与姓名
首字母处的句点。

展示公式必须整块保留。按行切会把一条公式拆成 `$$`、`\begin{aligned}`、`\mathcal F`、
`&=`、`\frac{...}`、`\end{aligned}`、`$$` 十几个碎片：整条公式不再是可检索单元，而每个
碎片还要各占一条向量、各付一次编码费用。未闭合的定界符退化成普通行处理，避免一个笔误
把后面整篇正文吞进同一个单元。

除 `$$` 与 `\[` 外，顶层数学环境（`equation`、`align`、`gather`、`multline` 等，含带星
号的变体）同样被识别为块起始，换一个直接产出 `\begin{equation}` 的上游转换器不必再改代
码。`aligned`、`cases`、`array` 这类只能嵌套在数学模式内部的环境**不**在此列——它们总是
被外层定界符一并吃掉，若也当作块起始，顶层误写时会吞掉后续正文。

#### 被公式夹断的句子会重新接合

"我们得到 [公式] 而 [公式]"在数学写作里是一句话，按行切之后会留下 `Therefore`、`and`
这类没有独立意义的残片。切句完成后有一趟合并：相邻片段属于同一句时并成一个区间，包括
中间的公式块在内，于是检索单元变回"完整的数学句子"。

合并规则收得很紧，只在与展示公式相邻时发生：

- 左侧片段已经以 `.`、`!`、`?` 结束 → 不合并；
- 右侧片段开启一个展示公式块 → 合并（散文引子 + 公式）；
- 左侧以公式结束定界符收尾，且右侧以小写字母开头 → 合并（公式 + `and`/`where` 之类续写）。

第三条要求小写开头，是因为公式之后另起大写字母多半是新句子，不该被吸进来。表格行同样
没有句末标点，但它们不与公式相邻，因此永远各自独立。

第三步是结构过滤（`index.is_indexable`）。以下片段不进入句子索引：

| 片段 | 理由 |
| --- | --- |
| `> Section: 章节 / 路径` | paper_markdown 为 retrieval_text 添加的前缀，信息已结构化在 `SearchHit.heading_path` 里 |
| `## 标题行` | 同上 |
| `\| --- \| :-: \|` 表格分隔行 | 不含任何可检索内容 |
| 不含任何字母词的片段（`$$`、`\[`、`[1]`） | 同上 |

表格**数据**行一律保留：方法名、数据集名、数字，正是检索最该命中的东西。参考文献不再
作为独立检索单元，改为解析成引用边，见下一节。

**为什么必须过滤。** 三个各自正确的设计叠在一起会产生系统性偏置：

1. 按行切分让每个结构行都成为与正文句平权的检索单元；
2. 余弦相似度对短文本有系统性偏置——只有一个词的向量"方向纯粹"，命中查询里任意一个
   词就能拿到接近上界的相似度，且不必覆盖查询的其余部分；
3. chunk 得分取其最高句得分（A-RAG 的设计，用平均会让长 chunk 被稀释），于是一个 chunk
   的排名由它最极端的那个句子决定。

问题不在第 3 步，而在"什么才配当一个可检索单元"。A-RAG 论文在 HotpotQA / MuSiQue 这类
维基段落上评测，语料是干净散文，没有这一层；把它搬到论文全文才出现。

过滤只按结构判定，不按长度判定：表格数据行常常只有数字与方法名，长度阈值会把它们一并
误删。

**实测（3 篇论文：2602.03442 / 2005.11401 / 1706.03762，273 chunk）**

| | 过滤前 | 过滤后 |
| --- | --- | --- |
| 索引句数 | 1775 | 1430（−19.4%） |
| 短于 40 字符的占比 | 28% | 14% |
| 句长中位数 | 70 | 88 |

同一条查询 `how are retrieved passages combined with the generator during training`：

- 过滤前前四名：`##### Baselines.` / `### Training` / `## References` / `## Training`，
  并列 0.378，全部是标题行。
- 过滤后前三名：`we run ablations where we freeze the retriever during training` /
  `We employ three types of regularization during training:` /
  `During training, we retrieve the top $k$ documents for each query.`

区间指向的仍是未经改动的 chunk 正文，因此 `paper_chunk_read` 返回的全文不受影响。

### 参考文献作为引用边，而不是检索单元

`build_corpus_index(..., index_bibliography=False)` 是默认行为：`kind == "bibliography"`
的单元不进入语料，改为被解析成**引用边**，挂在引用它们的正文 chunk 的 `cited_ids` 上。

**为什么改。** 实测一次真实全链路（5 篇 RAG 方向论文，见验收状态）里，参考文献占了语料
条目的 **45%**（277 / 614），而它们单条只有约 346 字符、语义稀薄。更关键的是，把参考文献
当文本索引，等于把一个**关系结构**拍平成了正文。

[SciRAG](https://aclanthology.org/2026.eacl-long.303.pdf)（Ding et al., EACL 2026）把当前
科学文献 RAG 的第一个局限就归结为这一点：

> **Superficial exploitation of citations**: references are treated as plain unstructured
> text rather than as structured relational entities, or, at best, single-hop backlinks,
> leaving the richer forward–backward citation graph unused.

Athena 此前同时命中了这句话的两半：参考文献作为纯文本进索引，而 `paper_scout` 的 `expand`
只做反向单跳。SciRAG 的做法是让参考文献退出检索文本，转而承担三件事：从初筛集合出发沿
**正反向各扩一跳**的 citation-graph expansion；按 T(theory)/E(experiment)/M(method)/
A(application) 给论文片段打概念角色标签，据此发现跨论文的概念链接（如 `[1]T→[2]E`）并剪
掉矛盾分支；最后抽出 **contribution chains** 并让模型在链上推理排序，而不是按相似度或中
心性打分。

**本仓库实现到哪一步。** 只做了其中最基础的一层——**语料内部的引用边**：

1. 每篇论文选一个落点（`paper_anchors`）：优先其 `abstract` 单元，否则第一个单元；
2. 逐条参考文献做标题匹配（`citation_edges`）：把条目文本规范化后，检查是否包含语料中
   某篇论文的规范化标题；命中即把该条目的 `[@key]` 连到那篇论文的落点；
3. 正文 chunk 通过自身的 `citation_keys`（paper_markdown 早就解析好了）查表，把命中的
   落点写进 `cited_ids`（`cited_paper_ids`）。

只认语料内部的引用：跨出语料的引用没有落点，留着只会让 Agent 读到 `not_found`。标题短于
20 个规范化字符不参与匹配，避免 "RAG" 这类短名误连；自引（同一命名空间）被排除。

**实测效果**（同一批 5 篇论文，同一份 store）：

| | entries | sentences | 引用边命中的 chunk | 图表链接 |
| --- | ---: | ---: | ---: | ---: |
| `index_bibliography=True`（旧行为） | 614 | 4974 | 26 | 156 |
| 默认（参考文献作为边） | **337** | **3957** | **19** | 156 |

条目减少 45%、句子减少 20%，图表双向链接不受影响；19 个正文 chunk 获得了指向被引论文的
跳转（例如 Atlas 的正文段落 → RAG 论文、ReAct 的表格 → RAG 论文）。检索侧的影响见验收
状态里的消融：方向上有利，但 40 题只差 2 题，未达显著。

引用边的数量受语料构成限制而不是受实现限制：这 5 篇里较新的两篇（IRCoT、When Not to
Trust）没有被同批其他论文引用，因此修复它们的脏标题并没有增加边数——标题修复影响的是
"别人能否引到我"，而不是"我能否引到别人"。

**与 SciRAG 的差距，以及尚未回答的问题。** "谁引用了本文"这条边现在由
`paper_cites(direction="cited_by")` 提供（见下一节），是从语料内部的引用边反向索引出来
的，不需要额外的网络调用；仍然缺的是角色标注（T/E/M/A）与 contribution chains。跨出语料
的引用依然没有落点，要补得靠 S2 的 `/citations` 端点。另外**没有任何公开工作做过"索引参
考文献 vs 不索引"的检索质量消融**，因此"45% 是否真的有害"目前只有结构性论证，没有数值证
据——`index_bibliography=True` 保留下来就是为了让这个对照可以在自家 benchmark 上跑出来。

## 检索语义

### paper_keyword_search

按 `Σ 词频 × 关键词长度` 给 chunk 打分，长关键词更具体因而权重更高。匹配不区分大小写，
以便实体名在正文与标题的不同写法下都能命中。返回 chunk id 与**只包含命中句**的片段。

### paper_semantic_search

句级余弦检索后按父 chunk 聚合，chunk 得分取其最高句得分。先取全局最高分的一批句子再
聚合，因此一个 chunk 只有真正命中的句子会进入片段，而不是整段正文。相似度非正的句子
一律排除。

语料未建向量、或建索引与查询用的模型标识不一致时明确报错，不返回一批无意义的相似度。

#### 自足度权重

余弦相似度先按 `self_contained_weight` 折算再排序：实词数少于 `SELF_CONTAINED_TOKENS`
（5）的片段按比例降权，实词为零的片段权重为零、直接出局。

结构感知切句去掉的是纯结构片段，剩下的仍有一类噪声：实词寥寥的正文片段——公式行、
纯数字表格行、参考文献条目的姓名部分。它们在余弦检索里占便宜的机理与标题行相同：向量
集中在少数维度，命中查询里任意一个词就能逼近相似度上界，却不必覆盖查询的其余部分。

**按实词数而不是按字符数**。反例足以说明必要性：`| | | | 0.2 | | 5.47 | 25.7 | |` 长
达 259 字符却一个实词也没有，字符阈值放它过关，实词阈值不会。

**只作用于语义检索**。这类片段恰恰是关键词检索的正当目标（按公式名、指标值或作者名
定位），因此 `keyword_search` 与索引本身都不受影响，权重也只在语料带向量时才计算。

#### 阈值取 5 的依据

在 7 篇论文、6 个学科（cs.CL / cs.LG / math.AP / physics.optics / q-bio.NC /
astro-ph.GA）、603 个 chunk、6662 个句子上做过一次扫描。查询取自某一篇论文的散文句，
只在**其他**论文的 chunk 里检索，因此查询不在答案集中，不需要人工标注：

| 阈值 | 首位是碎片（<5 实词） | 已经命中正文的查询被搅动 |
| --- | --- | --- |
| 关闭 | 41% | 0% |
| 3 | 23% | 0% |
| 4 | 13% | 0% |
| **5** | **2%** | **0%** |
| 6 | 0% | 8% |
| 8 | 0% | 26% |
| 12 | 0% | 51% |

5 是这条双边权衡的拐点：**最后一个完全不搅动既有正确结果的取值，也是第一个把碎片率压
到个位数的取值**。再往上碎片率的收益已经耗尽，代价却从 0% 跳到 11%、29%、57%。

分学科看，阈值 5 处的碎片率是 0%–5%，六个学科没有一个是例外；关闭时则是 55%–63%，
同样一致。因此这个取值不是在某一类论文上调出来的。

两点要注意：碎片率的判据（<5 实词）与阈值作用的量是同一个，二者并非互相独立，真正独
立的指标是"搅动率"，而 5 与 6 的分界正是由它划出的；此外整个扫描用的是一个词袋编码
器，短文本偏置在它身上最极端，换成神经编码器后问题与修正的幅度都会变小。

### paper_chunk_read

检索工具只给片段，全文必须显式读取。本会话内重复读取只返回一句提示，既省上下文也促使
Agent 去探索新的 chunk。`include_adjacent` 连同同一篇论文内的相邻 chunk 一并返回，越过
论文边界的邻居会被排除。

## 类型化边与类型化遍历算子

语料里同时存在两类关系，它们的语义完全不同：

- **图文互链**：正文 chunk 指向它讨论的图表（上游的 `visual_ids`），视觉单元指向讨论它
  的正文（上游的 `chunk_ids`）。这条边留在篇内。
- **引用边**：正文 chunk 指向它引用的、语料内部论文的落点（见上一节）。这条边跨篇。

**此前两者被并进同一个无类型列表 `CorpusEntry.related_ids`**——字面就是
`related_unit_ids(unit) + cited_paper_ids(unit, edges)`。这个字段的 docstring 自己就承认
了问题："the visuals a text chunk discusses, **or** the text chunks that discuss a
visual"：一个字段两种含义，Agent 拿到之后无法知道跟过去是一张图还是另一篇论文，只能盲跟。

现在拆成 `visual_ids` 与 `cited_ids` 两个字段，并按边的类型暴露算子：

| 算子 | 边 | 方向 |
| --- | --- | --- |
| `paper_visual_of` | 图文互链 | 双向，同一个工具 |
| `paper_cites(direction="cites")` | 引用边 | 正向：这些 chunk 引了谁 |
| `paper_cites(direction="cited_by")` | 引用边 | 反向：谁引了这些 chunk 所属的论文 |
| `paper_section_search` | 章节谱系 | 自顶向下，默认跨全语料 |

**为什么分开命名而不是合并成一个通用 `related`。**
[MRAgent](https://arxiv.org/abs/2606.06036)（Ji et al., ICML 2026）的 Table 6 实测：不同
问题类型激活的算子分布完全不同——时序类问题 86.5% 的证据来自时间算子，多跳类主要来自
标签算子（66.3%）与主题算子（46.0%）。一个通用相似度做不出这种区分，而**算子的选择本身
就是可观测、可评估的路由决策**：能统计"哪个算子贡献了证据"，就能知道该往哪投。

`paper_cites` 的反向方向补上了本文档此前记为"未实现"的那一项。它对下游尤其重要：Athena
的 RAG 要为假设找**支持与反驳双方**的证据，而语义检索按定义会优先返回与查询措辞最接近的
文本——**也就是同意它的那些**。反驳性证据几乎总是在另一篇论文里、措辞与假设相反。反向引
用边和跨论文章节切片是目前仅有的两条不带这个偏置的通道，`paper_semantic_search` 的工具
描述里因此明确写了这条局限并指向它们。

`paper_section_search` 默认不限定论文：对比性证据的典型位置是**另一篇论文的可比章节**
（Limitations / Ablation / Related Work），按章节名跨语料切片正是拿到它们的方式。

指向未被解释的视觉单元的链接会在建索引时剔除，引用边同样只保留语料内部可落点的目标。
没有配置 `VisualInterpreter` 时 `interpretation_status` 为 `unavailable` 的视觉根本不进
语料，留着链接只会让 Agent 读到 `not_found`。

没有图文互链这一层时，正文与图表之间唯一的关联是词面巧合——例如正文里的
`[fig:multi-head-att]` 恰好与图注里的 `**fig:multi-head-att**` 对得上。那依赖上游"交叉引
用未解析"这个缺陷；一旦上游把它渲染成 `Figure 1`，多篇语料里的 `Figure 1` 互相碰撞，关联
反而更差。

遍历类算子没有查询向量可用来挑句子，因此片段固定取 chunk 开头三句：正文的开头通常就是它
的主张句，图表单元的开头是图注。

## 试过但未采纳的两条 MRAgent 借鉴

这两条按 MRAgent 的论述都应该有效，实测在本模块的任务形态上不成立，**因此没有实现**。
数据见验收状态一节；这里只记结论，避免以后重复走一遍。

### 断言标签层（不适用）

原方案：由 `paper_markdown` 阶段的模型为每个 chunk 生成一行断言标签，检索侧多出一个只
扫标签的廉价通道。MRAgent 的消融显示，结构从 Cue→Content 变成 Cue→Tag→Content，**不加
任何推理**就能让多跳召回从约 58 涨到约 68。

实测三条都不支持把它留下：

1. **不划算。** Agent 级只加标签层的臂 surfaced recall 0.717 vs 基线 0.633（+0.084），
   代价是 prompt token **+52%**；同样一轮里类型化算子只多 25% token 就拿到 0.800。
2. **不能进主排序。** 标签单独检索 MRR 0.471（细节类）/ 0.701（断言类），都低于语义检索
   的 0.891 / 0.926；把标签交错融合进主排序反而把语义从 0.891 拉到 0.606。
3. **转换期成本被低估。** "一篇论文一次模型请求"在真实论文上不成立——86 个 chunk、48KB
   prompt 的单次调用 >300 秒未返回，必须由适配器分批，于是"一次调用"这个卖点也没剩下。
   索引侧还要多付 11% 的向量与 8.7% 的建索引时间。

保留判断力的部分：否定是**有条件的**（n=10、单轮实验），而且标签在断言型查询上的劣势
（−0.23）明显小于细节型（−0.42）。若下游变成"先粗筛断言、再定位细节"的两段式，值得重
测；重测前不该有代码。

### 深度优先的检索策略（不适用）

原方案：把 MRAgent 的预算结论（增加轮数 `T` 单调提升、增加单轮宽度 `K` 很快饱和）写进
两个检索工具的描述——本模块不实现 agent loop，工具描述是唯一能把策略送到模型面前的通道。

实测是负的：

| 臂 | surfaced recall | prompt tokens |
| --- | ---: | ---: |
| 基线 | 0.633 | 20 862 |
| 只加这段文字 | **0.391** | 17 771（**更少**）|

模型确实照做换成了更窄的查询——token 少 15%、更快——但本模块的证据是**成组**的：一篇论文
的全部引用者、一个章节下的全部 chunk。窄查询恰好不利于这种形状。同一轮的预算实验指向同
一结论：单轮宽检索 `T=1, k=15` 拿到 0.621 surfaced recall，只花 2 255 token；但它的
read recall 是 0.000——宽检索便宜地"看见"证据，"读进上下文"仍然必须靠轮数。

`DEFAULT_TOP_K` 保持 5、`MAX_TOP_K` 保持 20，均未改动。

需要注意这条否定只覆盖**本模块的任务形态**（gold 成组、n=10、单轮）。若下游出现真正的单
目标多跳查询，值得重测。

`paper_semantic_search` 描述里"它会低报反面证据，去用 `paper_section_search` 或
`paper_cites(cited_by)`"那段**保留**——它属于类型化算子，与深度指导无关。

### 会话状态

全部算子共享一个 `RetrievalSession`：按 `corpus_ref` 缓存已解码的语料，并记录已读集合。
检索与遍历都是纯读取因而 `concurrency_safe`；`paper_chunk_read` 会更新已读集合，故声明
为不可并发，由 agent loop 串行化。

## 与论文的差异

1. 不重新切分 chunk（保留 locator 溯源）。
2. 关键词匹配不区分大小写。
3. 片段有 600 字符上限——Athena 的 chunk 可达数千字符，不设上限会让"只返回片段"失效。
4. 语义检索排除相似度非正的句子，避免小语料下无关句被凑进片段。
5. 结构感知切句与自足度权重（见上），论文的维基语料不存在这个问题。
6. 不移植论文实验设定里"禁止并行工具调用"的约束——那是评测控制变量，不是接口契约。
7. 参考文献不作为检索单元，改为引用边（见上）；A-RAG 的语料里没有参考文献段落，这个
   取舍是论文语料特有的。
8. 三个类型化遍历算子不来自 A-RAG，来自 MRAgent（见上）；A-RAG 的语料是扁平的文档集
   合，没有图文互链、引用和章节这三类结构可走。

## 与 MRAgent 的差异

MRAgent 做的是**对话记忆**（LoCoMo / LongMemEval），不是文献检索，因此它的数字对本模块没
有预测力，能借的是结构主张。三条借鉴之外，刻意没有跟进的部分：

1. **不做逐句重写与 cue 抽取。** MRAgent 的构建管线（B.1）要求 LLM 重写每一句以消解代词、
   切分 episode、抽 cue、抽语义单元、再聚类 topic。按篇论文跑就是多趟全文调用。更粗的
   chunk 级标签层试过了，结论是不划算（见"试过但未采纳"）。
2. **不做 Topic 层。** MRAgent 的 τ 节点汇总跨 episode 的复现模式并提供自顶向下入口。对
   应到论文库就是"每个复现断言一个节点，指向所有主张它的 chunk"，这是结构上缺口最大也最
   贵的一块（需要索引期的跨论文聚类）。`paper_section_search` 只是它的廉价替身：按章节名
   而不是按断言做跨论文切片。
3. **它的可表达性定理（Theorem C.5）不构成设计依据。** 该定理证明自适应检索的假设类严格
   包含非自适应的，构造是二叉树 needle-in-a-haystack——节点 payload 里字面编码了下一步该
   走哪个分支。结论正确但不约束任何具体设计：任何自适应策略都满足它。
4. **摘要里的 23% 不是本模块的预期收益。** MRAgent 的 RAG 基线是单次 top-k，而 Athena 本
   来就是多轮 agent 循环，那部分增益已经拿到了。可迁移的是消融里"结构本身"的约 10 分。
5. **领域外推方向不利。** 对话记忆的实体图稀疏，论文的实体密度高一个量级，cue→tag 的扇出
   更差。MRAgent 关于组合爆炸的论证在论文语料上只会更强，因此标签层必须比它更有选择性。

## 备选方案：Contextual Retrieval

结构感知切句与自足度权重解决的都是"哪些片段不该赢"。它们解决不了另一半问题：**正文
chunk 本身也可能缺少自足语境**。"该变体在两个数据集上均下降 1.2 分"这样的句子，脱离所属实验设置后
既检索不到也读不懂。

Contextual Retrieval（Anthropic, 2024）的做法是在编码之前，由一个模型为每个 chunk 生成
一段说明它在全文中位置与角色的前缀，前缀与正文拼接后再嵌入；配合稀疏检索与重排使用。
公开结果显示它能明显降低检索失败率，代价是每篇论文额外的模型调用（可用 prompt caching
摊薄全文重复输入的成本）。

**当前状态：只保留契约，不接入链路。**

- `interfaces.ChunkContextualizer`——生成上下文前缀的供应商无关协议，与 `TextEmbedder`
  同级。
- `contextual.contextualize_entries`——保留的入口，调用会抛 `NotImplementedError`，而不
  是悄悄返回原样条目（后者会让调用方以为语料已经过上下文增强）。

Athena 目前没有配置任何 `ChunkContextualizer`，把半成品接进 `build_corpus_index` 只会让
语料在无声中分裂成两种不兼容的形态。真正落地前需要一并决定：

1. **前缀写到哪里。** 若并入 `CorpusEntry.text`，句子的字符区间与 `paper_chunk_read`
   返回的全文都会随之改变，模型会读到并非原文的内容；若只用于编码而不落进正文，则需要
   在 schema 里为编码文本单开一份来源。
2. **语料标识。** `embedding_model` 之外还需要记录是否经过上下文增强，否则两种语料混用
   时无法在查询期发现不一致——这正是 `embedding_model` 守卫要解决的同一类问题。
3. **成本归属。** 建索引已经是显式的库函数调用，增强属于同一次离线成本，但需要向调用方
   暴露可预估的用量。
4. **收益验证。** 需要一组论文级检索评测来确认增益，否则无法判断它是否值回模型调用。

更远的选项是 cross-encoder 重排：它显式建模片段对查询的覆盖度，是残留噪声最彻底的解法，
代价是每次检索一次模型调用。自足度权重可以看作它的零成本近似——只用"片段是否自足"这一
个先验，换掉了"片段是否回答了这条查询"的完整判断。

## 编码器要求：必须是神经编码，且要在装配期校验

这是本模块最容易出错、后果又最重的一处配置。**词法编码器能把语料照常建起来、检索照常
返回结果，只是结果等同噪声**——不会报错，不会降级，没有任何征兆。

同一份语料上的实测（口径见验收状态）：

| 编码器 | R@1 | R@5 | R@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| 神经（1024 维） | 0.250 | 0.675 | 0.800 | **0.417** |
| 词法 bag-of-words | 0.025 | 0.050 | 0.175 | **0.048** |

MRR 相差 8.7 倍，R@1 只有 0.025——40 题里对 1 题。

### 要求

组合根注入 `TextEmbedder` 时必须满足：

1. **是神经稠密编码器**，不是词频/哈希类的词法向量；
2. 建索引与查询使用**同一模型**（`PaperCorpusIndex.embedding_model` 会记下标识，不一致
   时语义检索明确报错而不是返回无意义的相似度）；
3. 启动时调用 `require_semantic_embedder(embedder)` 校验，不合格直接拒绝启动。

### 校验方式

```python
from athena.research.paper_rag import require_semantic_embedder

margin = await require_semantic_embedder(embedder)  # 不合格抛 NonSemanticEmbedderError
```

探针是三组「锚句 / 改写句 / 无关句」，锚句与改写句**刻意不共享实词**，因此词法编码器无法
把改写句排在无关句前面。判据是二者余弦相似度之差的均值，阈值 0.25。实测：

| 编码器 | margin |
| --- | ---: |
| 词法 bag-of-words | −0.013 |
| `qwen3.7-text-embedding` | 0.474 |

这一步刻意**不放进 `build_corpus_index`**：它要额外打一次模型，而单元测试用假编码器是
正当的。它属于装配期检查——一次错误注入会让之后每一次检索都无声地返回噪声。

## 已知限制

- 仓库内没有任何 `TextEmbedder` 实现。与 `paper_markdown` 的 `VisualInterpreter` 一致，
  只给协议不给具体适配器；未配置编码器时语料照常构建，语义检索明确报错。编码器必须是
  神经的，理由与校验方式见下一节。
- `paper_keyword_search` 在 chunk 全文上算原始词频，既没有 IDF 也没有长度归一，因此偏好
  长 chunk——与语义检索偏好短单元恰好相反。若要动打分，直接换 BM25 能一次解决这两点。
- 结构过滤不修复上游遗留的 LaTeX 残片（`\bibliography{custom}`、`acl_natbib`、`[!htbp]`
  等）。它们含字母词因而被保留，正确的修复位置在 `paper_markdown` 的 tex 解析。
- `self_contained_weight` 按字母段计数，而中日韩文字没有词间空格，整句会被算成一个实词
  （权重恒为 0.2）。当前语料全是英文论文因而未暴露，混入中文正文时会被系统性压低。
- 句子接合只跨展示公式。被行内公式、脚注或列表打断的散文仍可能留下短片段，它们会被自足
  度权重压住因而不影响排序，但仍各占一条向量。
- 引用边只按**标题字符串包含**匹配，没有做真正的参考文献解析。参考文献里标题被截断、
  换行改写或缩写时会漏连；反过来若一篇论文的标题恰好是另一篇标题的子串，会误连。要做稳
  就得像 GROBID 那样把条目解析成结构化字段，或直接用条目里的 DOI/arXiv id。
- 引用边只覆盖语料内部。语料内的两个方向都有了（`paper_cites` 的 `cites` 与 `cited_by`），
  但"谁引了本文"只能看到同批语料里的引用者；要覆盖语料之外的引用仍需接 Semantic Scholar
  的 `/citations`。
- `paper_section_search` 按章节名做子串匹配，不理解同义章节名。"Limitations" 命中不了
  "Discussion" 里谈局限的段落，也命中不了把局限写进 Conclusion 的论文。它是 MRAgent Topic
  层的廉价替身，不是等价物。
- 参考文献退出检索单元后，`paper_chunk_read` 读不到参考文献原文。若出现"这条引用的完整
  出处是什么"这类需求，应从 `PaperContent.bibliography_ref` 取，而不是恢复索引。

### 类型化算子与标签层的实测（2026-08-03）

**语料。** 12 篇跨子领域的机器学习论文（Transformer、BERT、BatchNorm、LayerNorm、

视觉解释走真实 VLM。语料引用 `sha256:c9475b83…`（无标签对照臂 `sha256:103e6169…`，同样

sentences=7100` 可与上面对上——这是本次唯一被逐项核对过语料身份的一批结果。

**查询构造。** 取自持有该边的正文 chunk 的开头两句。这不是改写测试，而是刻意模拟**算子
真正有用的那个时刻**：Agent 已经检索到讨论某图/引用某文的段落，现在需要一条边之外的东
西。两臂预算相同（各 ≤10 条），算子臂把一半预算花在平检索、一半花在跳一步。

**E2 一跳能到达什么**（25 题/任务）：

| 任务 | 平检索 | 平检索 + 一次算子 |
| --- | ---: | ---: |
| 引用跳（金标＝被引论文） R@10 | 0.200 | **1.000** |
| 图文跳（金标＝对应图表） MRR | 0.633 | 0.633（**无差别**）|

引用跳这一行里，"算子能到达"是构造决定的；真正的测量是**平检索有 80% 的情况到不了被引
论文**。图文跳则是一个诚实的负结果：我们的切分让图表成为原子 chunk，其正文本身就含图注
与解释，与独立视觉单元近乎重复，因此平检索直接就能找到，`paper_visual_of` 在这个预算下
加不出东西。它的价值要到"图里读出的数值与正文措辞不同"时才体现，本轮没测出来。

Related Work 与 Conclusion 上平检索**一条都没命中**：按查询措辞做语义检索不会把"综述式

**E1 标签通道单独测**（40 detail + 40 claim 题）：

| 通道 | detail MRR | claim MRR |
| --- | ---: | ---: |
| 语义（基线） | **0.891** | **0.926** |

0.23——与"标签承载主张、不承载数字"的设计意图一致，也是这条否定被记为"有条件"而非"无效"
的原因。合起来看，它唯一可能站得住的位置是廉价扫描层；而扫描层的收益（+0.084）抵不过它
的代价（+52% token），因此实现已移除，只保留结论。

| B（提交时状态） | 0.633 | 0.201 | 20 862 | 44.6 |
| **+① 类型化算子** | **0.800** | **0.289** | 26 180 (+25%) | 39.5 |
| +② 深度指导 | **0.391** | 0.166 | 17 771 (−15%) | 29.6 |
| +③ 标签层 | 0.717 | 0.192 | 31 799 (+52%) | 36.3 |
| +①②③ 全开 | 0.783 | 0.156 | 34 983 (+68%) | 37.3 |

**先说这张表能支撑什么、不能支撑什么。** 五个臂同语料、同题、同预算，**臂间可比**；但
`n=10`、温度 0.2，**没有重复实验**，因此每一行都应当当作方向性证据而不是点估计。

尝试过一次重跑，结果不能用作复现：评估脚本把语料引用写在固定路径的 `manifest.json`，而
一个迟到的旧格式构建在两次评估之间把它覆盖了，于是第二轮**静默地换了一份语料**（796 条目
/212 有标签，对比第一轮 792/791）。第二轮得到 B 0.342、`+①` 0.572——看起来像 0.25 的跑
间方差，实际主要是语料变了。**教训是评估脚本必须把 `corpus_ref` 连同结果一起落盘**，靠
可变路径传递语料是错的；当前脚本没有做到这一点。

`+①` 与确定性测量（引用跳 0.200→1.000、反向引用 0.133→0.945）方向一致，这是它目前最强
的支撑——确定性那部分不含 agent 方差。

`+②` 明显低于基线（0.391 vs 0.633）且 token 更少、更快。合理解释是深度指导让模型改用更
窄的查询，而本任务集的 gold 是**成组**的（一篇论文的全部引用者、一个章节的全部 chunk），
窄查询恰好不利。**MRAgent 的 depth>width 结论在我们这个任务形态上没有复现**——只有一轮，
不足以下定论，但足以说明这条指导不该无条件相信。

`+③` 高于基线但**代价最大**（+52% token），而 `+①` 用 +25% token 拿到更高的召回。三项
全开（0.783）没有超过 `+①` 单独（0.800），说明三者不是简单可叠加的。

**E4 深度 vs 宽度**（同一臂、固定检索预算）：单轮宽检索 `T=1, k=15` 拿到 surfaced 0.621，
只花 **2 255** prompt token、10.4 秒——即约 79% 的召回、**6% 的 token**。但它的
read recall 是 **0.000**：一轮没有时间去读全文。也就是说宽检索便宜地"看见"证据，而"把
证据读进上下文"必须靠轮数。

### 语义通道的首次真实测量（2026-08-02）

在此之前，仓库里没有任何 `TextEmbedder` 实现，历次实跑只能用词法 bag-of-words 编码器占
位——**"语义检索"这一路从未被真正验证过**。这次接入 1024 维神经编码器后补上了测量。

口径：5 篇 RAG 方向论文的同一份语料；抽 40 个 ≥500 字符的正文 chunk，由对话模型为每个写
一个只有该 chunk 能回答的问题，并明确要求改写措辞、不复用原文短语与方法名拼写；再测该
chunk 在检索结果中的名次（known-item retrieval）。

| 检索臂 | R@1 | R@5 | R@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| 神经编码 + 参考文献作为边 | 0.250 | **0.675** | **0.800** | **0.417** |
| 词法编码 + 参考文献作为边 | 0.025 | 0.050 | 0.175 | 0.048 |
| 神经编码 + 参考文献进索引 | 0.250 | 0.625 | 0.750 | 0.399 |
| 关键词通道（同一语料） | 0.025 | 0.100 | 0.125 | 0.049 |

**编码器是决定性的**：神经与词法的 MRR 相差 8.7 倍（0.417 vs 0.048），R@10 相差 4.6 倍。
此前所有"语义检索可用"的结论都建立在第二行那个基线上，**应视为未经验证**。

**参考文献退出索引方向上有利但未达显著**：三项指标一致占优（MRR +0.018、R@5 +2 题、
R@10 +2 题），但 40 题里只差 2 题，属于噪声范围。这是本文档此前指出"无公开消融"的那个
对照，现在有了自家数据，结论只能说"至少无害，且省掉 45% 的条目与 20% 的句子"。

**关键词一栏不能当作该通道的评价**：查询是刻意改写、避开原文用词的，正是为了隔离语义能
力，词面通道因此被结构性压低。它在实体名、方法名这类字面查询上的价值不受这组数字影响。

其余口径限制：n=40、单一 5 篇语料；生成问题与生成向量来自同一家模型，对神经一臂可能有
轻微系统性偏好，因此**跨 provider 引用绝对数值不安全，A/B 对比（同题同语料只换编码器）
更可信**。
