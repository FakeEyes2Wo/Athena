# 文献链路整改：从"跑得通"到"够用"

Status: current
Owner: Athena maintainers
Last verified: 2026-08-17
Source of truth: `src/athena/research/bench/`、`src/athena/research/survey/library.py`、
`src/athena/research/paper_scout/selection.py`、`src/athena/research/fork.py`

一次针对整条 Academic Survey 链路的整改，分六段落地，外加一轮真机对照（第六点五节）。本文记录每一段**改了什么、为什么
是这个改法、以及用什么数字判定它做成了**。

前置阅读：[Academic Survey 全链路](academic_survey_ch.md)、
[paper_rag 真机基准](paper_rag_benchmarks_ch.md)、
[文献语料接入 loop](corpus_ideation_ch.md)。

## 零、先纠正一个前提

整改开始前的判断是"链路太脆弱、效果太差，需要重建"。实际查下来：

> `paperscout 检索 → 文献池 → 下载 TeX/PDF → 转 Markdown → 建 RAG 索引 → 暴露查询接口`
> —— 这条链路**逐段都已存在，而且就是这个顺序**。

所以整改不是重画盒子。缺陷不在盒子的划分上，在**盒子之间交付的东西没有质量契约**，而且
没有任何一个能重跑的测量在盯着。按目标形态重写一遍，最可能的结果是把同样的缺陷再造一遍。

## 一、Phase 0：把一次性测量搬进仓库

整改前，这条链路的每一个质量数字——检索 MRR、缺摘要篇数、引用边密度——都出自一次性脚本，
而**脚本不在仓库里**（`paper_rag_benchmarks_ch.md` 结尾自己写明了这点）。仓库里的
`test_paper_rag.py` 之类全用 Fake 跑，验的是代码路径不是检索质量。

后果很简单：**任何改动都无法证明变好，任何回归都不会被发现。** 所以第一件事不是改链路，
是先能量它。

`athena.research.bench` 给出三把尺子：

| 命令 | 回答的问题 | 是否需要模型 |
|---|---|---|
| `Athena-cli bench retrieval` | 改写过的提问能不能找回那篇论文 | 语义通道需要编码器 |
| `Athena-cli bench health` | 这份语料的结构够不够用 | 不需要 |
| `Athena-cli bench overlap` | 同一查询两次交付的论文重合多少 | 不需要 |

两处口径上的讲究，都是被真实数据逼出来的：

- **名次按论文算，不按 chunk 算。** 按 chunk 算会让"名额被一篇吃光"这种失败反而抬高
  分数，而那正是关键词检索真机上最严重的失效。
- **章节覆盖按全部标题层级统计**，因为 `section_search` 就是这么匹配的。只看一级标题会
  把 Ablation 报成 0/44——它几乎总是 `Experiments / Ablation Study` 这样的子节，于是这个
  数字回答的就不再是"该算子找不找得到反面证据"。

金标不在语料里的查询单独列出、**不进任何通道的分母**：那是出题问题或语料构成变化，算进
未命中就是让检索背一个不属于它的锅。这一步在真机上当场抓出过一个错标。

查询集（`bench/datasets/imbalance_auc.json`）是版本化输入数据，每条带 `rationale`——金标
改动会让前后两次基准不可比，而这种不可比是静默的，必须能在 diff 里看见。

## 二、Phase 1：语料 → 论文库

整改前每次调研都从零开始。实测一次 10 篇的调研 13 分 45 秒：

| 段 | 耗时 | 主要成本 |
|---|---|---|
| scout | 581s（71%） | 4 次策略 + 几十次打分 |
| source | 68s | HTTP，arXiv 限速 1 req/3s |
| markdown | 141s | 93 次视觉调用 |
| index | 29s | 257 批编码 |

这四段的输入**全都由内容决定**。`PaperLibrary` 按内容键把三样东西存下来，跨运行、跨项目：

- 检索结果（键：整份 `ScoutRequest` 的规范 JSON）
- 转换产物 `PaperContent`（键：paper_id + 源引用 + 转换器版本 + 视觉策略）
- 句向量（键：`PaperContent` 引用 + 编码器标识）

外加把 `LocatorCache` 落到盘上——它一直支持 JSON 持久化，只是 pipeline 从没传过 path。

### 几处必须的设计

**库和输出用两个存储。** 语料索引必须落在调用方给的那个 store 里（loop 用项目目录那份），
否则 `corpus_ref` 在宿主里解析不到——这条链路已经为这件事吃过一次亏。而缓存要跨项目共享
才有意义。命中时把索引真正要读的 blob 复制进目标 store，内容寻址让复制不改变任何 ref。

**半份内容一律判未命中。** 缺一个正文 blob 不会报错，只会建出一个检索永远返回空的语料。
向量同理：行数与句子数对不上就重新编码，绝不交出错位的矩阵。

**键里带版本。** `CONVERTER_VERSION` / `INDEX_VERSION` 改了缓存自动失效。需要人记得手动
清的缓存迟早会喂回过期结果，而那种错误只表现为"这次改动没效果"。

**检索缓存默认开，`--fresh-scout` 关。** 同一份请求是确定性输入；想要新的一批论文应当
明确说出来，而不是靠"每次都重跑"碰运气——那种"随机性"正是 Phase 2 要修的缺陷，不是特性。

验收：同一请求跑第二遍，检索 0 次、转换 0 篇、`corpus_ref` 与第一遍逐字节相同。

## 三、Phase 2：选片从散列抽签换成分面覆盖 + 边界档重排

这是整条链路唯一一处**信号被随机毁掉**的地方。

打分是四档离散的，交付名额几乎总是在某一档内部被截断。真机实测一轮：8 篇满分直接入选，
剩下 5 个名额由 **35 篇同为 0.45 的论文**争夺，胜负由 `tie_break` 的 sha256 决定——那是
刻意设计成"无偏"的，也就是刻意设计成**无信息**的。后果：同一查询两次跑测，交付的 10 篇
里只有 2 篇相同。

下游做得再对也救不回这一步。语义检索 MRR 已经很高；任务主指标是 ROC-AUC 时语料里三篇讲
AUC 的论文一次都没被引用，不是检索没找到，是选片没保证它们在。

一次模型调用做两件事：

1. **边界档重排**——只重排跨过截断线的那一档，已确定入选的不参与（它们分数本来就更高，
   重排等于用更弱的信号覆盖更强的）。调用数与档大小无关，每轮固定一次。
2. **分面覆盖**——把课题拆成若干面并标注每篇覆盖哪些面，填名额时先补没覆盖的面。
   "十篇都很贴题但全在讲同一个方法"是真实发生过的失败，而按相关性排序无法表达它。

三条边界：`max_papers=0` 在 `ScoutRequest` 里的含义是**不截断**（第一版把它读成"零篇"，
而真机默认值正好是 0）；边界档装得下时不发起调用；模型不可用/解析失败/返回空排序一律
回退散列次序——选片必须永远给得出结果。

回退理由记在 `ScoutStats.selection_note`，**不进 `errors`**：降级的选片不是失败的运行，
混进去会把真正的后端故障顶掉，也会把整轮标成 `partial`。

验收指标是 `bench overlap`。真机上拿两份既有语料试了一次：**0.080**。

## 四、Phase 3：修好语料的前门，加一条融合通道，向量走 mmap

### 门面锚点不再落在表格上

一篇论文的"落点"有三个消费者：`paper_corpus_overview` 的摘要、引用边的指向、写进 Ideator
提示词的语料目录。整改前规则是"优先 abstract kind，否则取第一个 chunk"，而 **44 篇里 20 篇
根本没有 abstract chunk**——退化之后 3 篇的门面是表格、1 篇是插图，还有几篇只有标题和作者名。

`anchor_index()` 改成：优先 abstract；否则在前 6 个里取第一个"有实质正文"的，跳过
表格/插图/公式/参考文献。"有实质正文" = 扣掉 `> Section:` 前缀、论文标题和 `\command`
形态的 LaTeX 命令之后还剩多少实词。

规则**只有一处定义**，`search` 的总览与 `bench` 的体检都 import 它。两处各写一遍的话，
体检会在规则改动后继续报旧行为——"尺子和被测对象各说各话"是最难察觉的一类错误。

真机复核（同一份语料，只换代码）：

| | 整改前 | 整改后 |
|---|---|---|
| 门面几乎无正文的篇数 | 5 | **0** |
| 锚点落在表格 / 插图 | 3 / 1 | **0 / 0** |
| 仍无真正 abstract chunk | 20 / 44 | 20 / 44（上游解析问题，未动） |

### 融合检索：先量，赢了才上

先作为 bench 的一条通道量，再决定要不要接进工具表。同一份 44 篇语料、12 条改写查询：

| 通道 | hit@1 | hit@5 | 未命中 | MRR |
|---|---|---|---|---|
| `paper_keyword_search` | 5/12 | 11/12 | 0 | 0.601 |
| `paper_semantic_search` | 9/12 | 11/12 | 1 | **0.833** |
| **`paper_search`（RRF 融合）** | 7/12 | **12/12** | **0** | 0.778 |

**融合的 MRR 比纯语义低，但它是唯一没有未命中的通道，且 hit@5 满分。** 这个取舍对本场景
是对的：Ideator 的失败从来不是"该读的论文排在第 2 而不是第 1"，而是"它根本没进视野"。
只看 MRR 会把这次交换读成退步——`compare()` 逐条比对正是为此写的。

融合按名次而不是分数：词面分是 `Σ 词频 × 关键词长度`（无上界），语义分是加权余弦（0..1），
任何线性相加都要先猜一个归一化，而那个猜测会随语料大小漂移。

### 查询向量缓存 + 向量 mmap

语义检索 96% 的时间是一次编码 API 往返，而三条 Ideator lane 拿到的是同一个任务、同一份
语料，问出来的话高度重合。缓存挂在 `CorpusCache` 上，按编码器分桶。

向量装载改走 numpy mmap，真机同一份语料实测：

| | 装载 | 峰值常驻 | 首查 | 热查 |
|---|---|---|---|---|
| 读字节 | 0.413s | 519 MB | 5.1ms | 3.5ms |
| **mmap** | **0.247s** | **367 MB** | 16.7ms | 3.8ms |

省 152 MB、装载快 1.7 倍，代价是首次查询多 11.6ms——相对那 137ms 的 API 往返可以忽略。

## 五、Phase 4：让文献到得了写代码那一步

消费端是价值流失最多的一处：语料只到得了 Ideator，而且只到一次。

**PlanAgent 拿到检索算子。** 整改前 `register_plan_agent` 的 `extra_tools` 只有 Kaggle，
于是文献只能影响"试什么"，永远影响不了"怎么实现"——而后者才是论文真正给得出细节的地方。
同时把"这条假设引了谁"拼进 plan 的 **content**（走 content 不走 `context_refs`，后者到
不了 model，这条学费已经交过）。

`corpus_tools(for_ideation=False)` 是新的默认：PlanAgent 的会话**不进**引用核验的已读
账本。默认设成不追踪，是为了让以后新增的消费方不会无声地放宽核验。

**补一轮 ideation 的触发条件改成"语料版本变了"。** `corpus_ideation_done: bool` →
`corpus_ideated_ref: str | None`。语料现在可以增量扩充，布尔标记会让扩充进来的新论文
永远读不到。旧 `state.json` 由 before-validator 迁移——`extra="forbid"` 下直接删字段会让
续跑崩掉，而不是降级。

**引用支持性判定。** 前两版核验查的都是**行为**（id 在不在语料里、本轮打开过没有）。一个
读过《数据增强综述》再拿它去支持"两两交互特征工程"的 Ideator，两版都过得去——而那正是
真机上实际发生的事。新增一层查**内容**：把被引论文里真读过的那几段交给模型，问"这段话
支持这条主张吗"。主张和干预都进提示词——只给主张，判定就退化成"这篇论文和这个话题相关吗"。

两个方向相反的保守取值：

- **单条判定**解析不出来 → 判不支持。误删一条真引用只少一份可追溯性；放行一条假引用会
  让没有根据的干预看起来有据可依。
- **整层不可用**（端点抖动）→ 保留原引用。这一层是增益，不该因为一次抖动就把已经通过
  前一关的结论清空。

## 六、Phase 5：让 A/B 第一次答得了原问题

"文献接地到底有没有用"至今**正反都没有证据**。上一次 A/B 答不了它，问题不在执行而在设计：
两臂各跑各的 PREPARE，于是各自写出一个 evaluator、各自训出一个基线。同一任务、同一数据，
两个基线的强弱就能差 0.03 以上，而 SEARCH 的改进也就 +0.05 量级——**基线方差与待测效应
同量级**。

`fork_project()` / `--fork-from` 把三样固定下来：同一个冻结 evaluator、同一个基线 commit、
同一份 artifact 存储。只让 `--survey` 不同。

```bash
Athena-cli run --project arm-off --fork-from prepared --data ...
Athena-cli run --project arm-on  --fork-from prepared --data ... --survey
```

三条不显眼但必须的规则：`corpus_ref`/`corpus_ideated_ref` 必须清空（它们正是被比较的那个
变量）；`phase` 直接落到 SEARCH（重跑 PREPARE 等于把要固定的那两样又变回变量）；目标已
存在时报错不覆盖（一条臂被另一条覆盖掉，表现出来是"分数怎么变了"，不是一条错误信息）。

## 六点五、真机对照（2026-08-17）：检索深度，以及一个被它揪出来的缺陷

只跑 scout 段，两臂 `max_papers` 都取 20，只让 `search_top_k` 与 `max_seconds` 一起变。
不跑取源/转换/索引：要测的是"gold 有没有进池"，下游三段既不改变池子，又要花掉大半墙钟
和全部视觉调用。query 沿用文档里用过的那条，便于与历史读数对照。

| | shallow（10 / 600s） | deep（50 / 1800s） |
|---|---|---|
| 候选池 | 120 | **285** |
| 满分 1.00 | 2 | **18** |
| 0.45 | 25 | 36 |
| 0.20 | 93 | 231 |
| 墙钟 | 988s | 1116s（**+13%**） |
| 步数 / 停止原因 | 6 / max_steps | 6 / max_steps |
| 打分调用 | 9 | 23 |
| 后端请求 | 24 | 61 |
| 无源剔除 | 60（50%） | 88（31%） |
| 边界档 | 48 篇（在 **0.20** 档） | 21 篇（在 0.45 档） |

**满分论文 2 → 18，墙钟只多 13%。** 步数没变——深度不需要更多步，只是每步取回更多。
无源剔除的比例也从 50% 降到 31%：深一点捞到的开放获取论文比例更高。

交付构成是最直观的：deep 的 20 篇是 14×1.00 + 6×0.45，逐条切题（惩罚化逻辑回归、focal
loss、正则化集成、LASSO、稀疏树正则、DRO、GBDT 损失函数）；shallow 只能凑出
1×1.00 + 11×0.45 + **8×0.20**，那 8 篇是图像分类、XGBoost 原论文、电池热失控、手机恶意
软件、心脏病预测——池子里根本没有 20 篇好的。

**`max_papers` 提到 20 只有在池子够深时才是收益**，否则它把噪声一起交付出去。这两个
参数必须一起看。

### 这轮对照揪出的缺陷：边界重排从来没生效过

两臂的 `selection_note` 都是：

```
selector failed (APITimeoutError); fell back to hash order
```

Phase 2 加的那次重排**一次都没跑起来**。回退逻辑是对的，所以它安静地退化成散列次序、
没有任何报错——又一个"安静地成功"。单元测试全绿，因为它们喂的是 Fake。

修法冲着延迟的成因：摘要 700→320 字符、一次最多排 40 篇、输出去掉逐篇 `why`（本仓库
早就测过延迟由输出 token 决定）、超时 120→300 秒。在**真实池子**上复测：

| | 边界档 | 重排 | 耗时 | 分面覆盖 |
|---|---|---|---|---|
| deep(285) | 21 | ✅ | 114.3s | **100%** |
| shallow(120) | 48 | ✅ | 219.0s | 75% |

残余风险：40 篇约 219s，离 300s 不宽裕。

### 另一件顺带查清的事：`max_seconds` 是软预算

shallow 臂 `max_seconds=600`，实跑 **988 秒**。预算只在每步**开始前**检查一次，所以一轮
的墙钟可以超出预算最多一整步。它一直是个"下一步要不要开始"的判据，不是硬上限。

## 六点六、打分粒度：更细的分让交付**更不稳**（2026-08-17）

四档打分导致同分成堆，直觉上的修法是让分数更细。真机测了三种方案，同一批 48 篇竞争论文
（18 满分 + 30 中档）各打两遍，主指标是**交付 20 篇的集合有多稳**：

| 方案 | 取值数 | 截断处同分 | 两次一致率 | Spearman | **top20 Jaccard** |
|---|---|---|---|---|---|
| **四档（现状）** | 3 | 13 | 0.812 | **0.905** | **0.818** |
| 0–10 档 | 10 | 9 | 0.396 | 0.894 | 0.667 |
| listwise 全体排序 | 48 | 1 | 0.083 | 0.691 | 0.667 |

**粒度和稳定性是反着走的。** listwise 的粒度完美——48 个不同值、零同分——却是排序相关性
最差的一个（0.691）。0–10 档看起来是个折中，实际两次一致率只有 0.396。

这就是"把噪声写得更精确"：更细的刻度没有带来更多信息，只是让同一份抖动表达得更充分，
而抖动会直接变成交付集合的churn。**结论是保持四档。**

### 但同一份数据也回答了"那边界重排算什么"

边界重排就是 listwise，按上表它应该同样不稳。同一份池子跑三次实测：

```
run1/2/3  重排=True  覆盖=100%  边界档=21
          分面三次完全相同：Class Imbalance / Tabular Data / AUC Optimization / Regularization Methods
两两 Jaccard [0.905, 0.905, 0.818]   均值 0.876   稳定核心 18/20
```

**0.876，比全体 listwise 稳得多。** 原因正是它的设计意图：交付的 20 篇里 18 篇是满分档，
**重排根本不碰它们**；只有 2 个名额由 21 篇的边界档决定，抖动因此被限制在边缘。

于是有一条可以复用的原则：

> **把不稳但有信息的信号，只用在稳定信号没有信息的地方。**

全体 listwise 违反它——它用一个 Spearman 0.691 的信号覆盖了分档已经给出的可靠区分；
边界重排遵守它——分档在同分档内部本来就没有信息，那里用什么都不会更差。

代价是相对纯散列（确定性，Jaccard 恒为 1.0）损失 0.124 的稳定性，换来 100% 的分面覆盖。

## 六点七、检索深度还能再深吗（2026-08-17）

重放 deep 那轮 Agent 自己发的 2 条查询，不跑 LLM：

| 深度 | 唯一论文 | arXiv 返回 | S2 返回 |
|---|---|---|---|
| 10 | 37 | 20 | 20 |
| 50 | 161 | 100 | 100 |
| 100 | 256 | **100（不变）** | 200 |
| 150 | 73 | 100 | **0（整条挂掉）** |

三个结论：

1. **50 正好是 arXiv 的饱和点**（`ARXIV_MAX_RESULTS = 50` 是本仓库设的硬上限），再深只
   影响 Semantic Scholar。这就是默认取 50 的理由。
2. **150 会让 S2 整条通道静默消失**——它的 `/paper/search` 超限不是截断而是返回非 2xx，
   本层抛 `BackendError`、该次动作返回 0 篇，看起来像"这个查询没搜到东西"。已加
   `SEMANTIC_SCHOLAR_MAX_RESULTS = 100` 夹紧。
3. 100 比 50 多出的 95 篇**变差但不是废物**：

   | | ≥0.45 密度 | 满分 |
   |---|---|---|
   | depth ≤50 的 161 篇 | 16.8% | 6 |
   | depth 100 新增的 95 篇 | 10.5% | 2 |

   密度是核心区的 63%，里面有 Stochastic Proximal AUC Maximization、Novel regularization
   method for the class imbalance problem。所以 100 值得作为选项暴露，但不做默认——默认
   要的是"每一篇都值得转换"。

**`expand_top_k` 不是杠杆**：池子主要靠 expand 长大（deep 那轮 search 2 次 / expand 20
次），但 expand 从没打满 20 的上限（shallow 7.1/次、deep 15/次）。

**进语料的 20 篇全部 ≥0.45（6×1.00 + 14×0.45），没有一篇 0.20。** 对照浅检索那轮交付里

### 这轮暴露的问题

**一、重排对准了错误的截断线（已修）**

报告里 `边界档=197 已重排`。但取源试到第 36 篇就够数停了——那 197 篇同为 0.20 的尾部
**一篇都没被碰过**。原因是选片用的 limit 是 `max_papers`（候选上限 60），而不是
`stop_after_fetched`（真正的交付量 20）。于是重排精心排了一批永远不会被下载的论文。

真正有人争的是 0.45 那一档：65 篇竞争约 14 个名额。改成按交付量切档之后，截断线才落在

**二、引用边基本为零**

新语料 20 篇之间只有 **1 条**引用边（每篇 0.05），比 44 篇语料的 16 条还稀。`paper_cites`
与 `cited_by` 在生产尺寸上是死的。根因未变：引用边靠标题子串匹配参考文献连出来，而
S2/OpenAlex 在检索阶段返回过的真实 references 一直被丢掉。这是整改里唯一一条列了却没做的。

**三、摘要覆盖仍是 50%**

10/20 篇没有 `abstract` kind 的 chunk。门面已经不落在表格上了（那是本次整改修的），但

**四、`Athena-cli survey` 全程静默**

18.7 分钟的命令，除了最后的报告没有任何输出。`SurveyPipeline` 支持 `emit`（loop 里用的
就是它），但 CLI 这条路没订阅。看上去与卡死无法区分。

**五、`scout_status: partial` 的原因是 `semantic_scholar`**

零星 429。`final_status` 已经不再沿用它（那是上一轮整改修的），总状态正确地报了
`complete`，但 `warnings` 里这一条值得留意——S2 无 key 时会更频繁。

## 六点九、引用图与召回基准（2026-08-17 续）

### 真实引用图：修好了，但没有救活那两个算子

解析参考文献那条路要求被引论文的**标题**在引用方的参考文献文本里匹配得上。改成用
Semantic Scholar 在检索阶段本来就返回、却一直被丢掉的 references 之后：

| | 边数 | 密度 |
|---|---|---|
| 解析参考文献（原） | 1 | 0.05 边/篇 |
| 真实 references（新） | **3** | 0.15 边/篇 |

19/20 篇解析成功、共取回 **1028 条参考文献**，落在语料内的只有 3 条。
**我给这一条定的验收标准是"提升一个量级"，没达到。**

根因不在边的抽取，在语料的构成：20 篇是按主题相关性挑出来的**样本**，不是一个引用邻域，
互相引用本来就少。所以 `paper_cites` 与 `cited_by` 在 N=20 上仍然接近不可用，换一个更好
的边来源救不了它。要让这两个算子真正可用，得改**选片**——让语料沿引用邻域生长（种子 +
它引的 + 引它的），而那是另一种语料，不是"最相关的 N 篇"。

改动仍然保留：真实 references 是正确的事实来源，解析标题只是近似；而边数随语料规模是
平方级增长的。

层的位置也是一处教训：第一版写在 `SurveyPipeline` 里自己 `build_backends()`，结果单测
直接打到真实网络上（一个文件从 8 秒变 104 秒、31 条失败）。reference backend 本来就是
注入给 scout 的，那里才是它的位置。

### 召回基准：把损失拆成三段

已有的 known-item 量的是"进了语料的能不能被找到"，而大头在它上游。新的
`Athena-cli bench recall` 把损失拆开报，因为三段的修法完全不同：

| 池子 | 进池（检索） | 判为相关（打分） | 进交付（名额与取源） |
|---|---|---|---|
| shallow 120 | 14/83（0.169） | 13/83（丢 1） | 7/83 |
| deep 285 | **29/83（0.349）** | 14/83（**丢 15**） | 8/83 |
| 352（金标源） | 83/83 | 83/83 | 56/83 |

两件汇总指标会藏起来的事：

1. **检索是压倒性的大头**——shallow 在这一段丢掉 69/83。深检索把进池召回翻了一倍。
2. **deep 那一段打分又丢了 15 篇。** 同一批论文、同一个打分器，换一次运行就掉出 0.45 线。
   这正是"四档两次一致率 0.812"的规模化表现——约两成论文会换档。

金标是**代理**：来自目前跑过的最强配置判定为 ≥0.45 的那 83 篇，`gold_source` 是必填的散文
字段。它回答的是 R@all 那个问题（更便宜的配置能捞回多少），不能回答"到底存在多少"。
第三行是金标自身，召回 1.000 是构造使然，留着作自洽性检查。

### A/B：机制验到底了，实验缺数据集

阻塞理由（"NEXT 1 会改变被测对象"）已经不成立——引用图改动几乎没有改变语料。但真机 A/B
仍然跑不了：**本机没有可用的数据集**，而 A/B 需要先有一次完整的 PREPARE（EDA + 写
evaluator + 训基线）才能分叉。

能在没有数据集时验的那一步已经验了：新增一条集成用例，用**真 git 仓库 + 真 artifact +
真 research_tree** 构造一个"PREPARE 已完成"的项目，分叉成两臂，再各起一个
`ResearchRuntime`，断言两臂的 `(evaluator_ref, phase, corpus_ref, sota)` 逐字段相同。

这一步值得单独验，因为它正是会静默失败的那种：`corpus_ref` 曾经因为写在一个库、读在另一
个库而长期取不到，症状只是"Ideator 一个算子都没有"。两臂起点不一致同样不会报错，只会让
分数悄悄不可比。

## 六点十、两遍打分的真机核对（2026-08-17）

改完之后跑一次完整链路核对，同一条 query。**"单测全绿"在这条链路上不构成"能用"的证据**，
所以这一轮专门去验三件事：它跑没跑起来、贵了多少、有没有别的东西被带坏。

### 跑起来了，而且证据是硬的

| | 上一轮（单遍） | 本轮（两遍） |
|---|---|---|
| 分数分布 | `1.00:18 · 0.45:65 · 0.20:269`（3 个取值） | `1.00:6 · 0.72:5 · 0.45:23 · 0.33:21 · 0.20:168 · 0.10:21`（**6 个取值**） |
| 打分调用 / 池子 | 29 / 352 = 0.082 次每篇 | 38 / 244 = **0.156 次每篇（1.89×）** |
| 检索缓存 | — | **检索重跑**（缓存键改动生效） |

`0.72 = (1.00+0.45)/2`、`0.33 = (0.45+0.20)/2`、`0.10 = (0.20+0)/2` —— 中间取值只可能来自
两遍取均值。每篇调用数 1.89× 也正是设计值。

### 边界档塌得比预测多得多

| | 上一轮 | 本轮 |
|---|---|---|
| 边界档 | **197 篇** | **14 篇** |

离线在 60 篇样本上估的是"少约 23%"（39 → 30），真机是 **少 93%**。原因是截断线的位置：
取值从 3 个变成 6 个之后，第 60 位不再落在 0.20 那条长尾里。副作用是重排那次调用也便宜了。

### 代价：我低估了

| | 上一轮 | 本轮 | 变化 |
|---|---|---|---|
| scout | 631.1s | 880.6s | **+39.5%** |
| 全程 | 1120.1s | 1495.9s | +33.6% |

**我预估的是 +10~20%，实测 +39.5%。** 而且本轮池子更小（244 vs 352），要打分的论文更少却
更慢——按每篇算涨得比墙钟显示的还多。

### 不能归因给打分器的那些

进语料的相关性构成看起来降了（`{1.00:6, 0.45:14}` → `{1.00:1, 0.72:3, 0.45:12, 0.33:3}`），
但**两轮的池子不是同一个**（352 vs 244，检索本身有方差），可取源的高分论文因此更少、只能
往下够。n=1 对 n=1、且自变量不止一个，**这条差异归不了因**。

同理，多遍打分要改善的是**跨运行的可复现性**，而那恰恰是两次池子不同的运行测不出来的。
离线那组测量（前 10 篇 Jaccard 0.594 → 0.809，样本 28–280）仍然是目前唯一的证据。

### 顺带确认与顺带发现

- **引用图第一次真的产出了边**：语料内 8 条 / 19 篇（0.42 边每篇），而独立测那次是 3 条 /
  20 篇。仍然稀疏，但比"1 条"那个起点已经不是一个量级。
- 摘要覆盖 50% → 63%，门面几乎无正文仍是 **0 篇**。
- **一处退化**：转换 20/20 → 19/20（失败率 5%），视觉调用失败 0 → 4。单次运行不足以判断
  是回归还是上游波动，下次跑测要盯。

## 六点十一、换掉打分策略：同分交给交叉编码器（2026-08-17）

六点十把两遍打分的账算清楚之后，结论是它买到的东西（可复现性）确实存在，但每次多花
4 分钟。于是回过头问一个更根本的问题：**两遍取均值是不是在治症状。**

### 病根在 `scorer.py` 里已经写着

打分器是四档离散的，而它离散的原因是通用 instruct 模型在二选一判断上给的是饱和概率
（`TokenProbabilityScorer` 那一节实测过：判决 token 概率 `' False':1.000`，其余全 0）。
论文的连续 ρ 来自 `pasa-7b-selector`——一个**为这件事微调、输出分布经过校准**的判别器。
那句话的推论是：要拿回连续分数，得换判别模型。

**交叉编码器就是那个判别模型。** 之前一直没往这个方向看，是因为把"换打分器"默认理解
成了"换一个更强的 LLM"。

### 先否掉两条更便宜的路

**`seed` 参数不管用。** 端点收下它但不兑现：同一 seed 连发三次给出三个不同答案，
`system_fingerprint` 为 `None`。顺带这次探测本身就是抖动的现场演示——4 篇论文、3 次
调用、3 个答案。

**更细的分档早就否掉了**（见六点六）：加分辨率只是把同一份抖动表达得更充分，交付
稳定性反而从 0.818 掉到 0.667。

### 接进来之前必须先验的两件事

`gte-rerank-v2` 在账号上可用，返回连续分数。但论文是分很多次动作陆续进池的，每次
`_absorb` 的批次大小都不同，所以：

| 要验的 | 做法 | 结果 |
|---|---|---|
| 跨批次可比 | 同 5 篇探针放进 5/15/20/30/50 篇批次，换伴随文档（随机 vs 全高分），换位置 | 最大偏差 **0.000116** |
| 确定性 | 同一批 352 篇连发三遍 | 逐篇分差均值 0.000034，top-N 排序 Jaccard **1.000 ± 0.000** |
| 分辨率 | 352 篇的取值个数 | **314 个**（打分器：3 个） |
| 成本 | 352 篇打完 | **0.4 秒**（打分器单遍 ~220 秒） |

第一条是硬前提：如果分数是批内归一化的，跨批次比较就没有意义，整个方案不成立。

### 决定性对照

用生产里真正的 `tie_break()`、60 篇真实池子、8 遍独立打分，不同遍之间的 top-N Jaccard：

| 配置 | 前 10 篇 | 前 20 篇 | 前 30 篇 |
|---|---|---|---|
| 1 遍 + sha256 拆平局（最早） | 0.599 ± 0.202 | 0.690 ± 0.161 | 0.777 ± 0.073 |
| **1 遍 + rerank 拆平局（现在）** | 0.692 ± 0.183 | **0.791 ± 0.090** | **0.896 ± 0.053** |
| 2 遍取均值 + sha256（六点十） | 0.742 ± 0.076 | 0.730 ± 0.078 | 0.784 ± 0.059 |
| 2 遍取均值 + rerank | 0.823 ± 0.096 | 0.753 ± 0.052 | 0.915 ± 0.029 |

**在生产实际截断的位置（交付目标 20 篇、`max_papers` 60），一遍加 rerank 直接赢过两遍
取均值**，而后者要多付 40% 的 scout 墙钟。

机制对得上：60 篇里 **39 篇同为 0.20**、9 篇同为 0.45，前 20 名的第 15–20 位全是从那个
39 路平局里挑的，而挑法是 sha256——故意没有信号。**churn 的大头从来不是档位翻转。**

前 10 篇那一格两遍取均值至今仍略优（0.742 vs 0.692），两者标准差 0.076/0.183 重叠，
而生产不在那个位置截断。`passes` 参数因此保留而不是删掉。

### 为什么不让它当主打分器

拿它和打分器比排序质量的那次对照，金标是**打分器自己 4 遍均值 ≥0.45 的 28 篇**：

| top-N | rerank 命中 | 打分器命中 |
|---|---|---|
| 20 | 8 | 13 |
| 30 | 12 | 15 |
| 60 | 16 | 18 |
| 100 | 22 | 21 |

这局天然偏袒打分器——金标是它自己的意见。**这张表只能读成"两者不一致"，读不出谁对**，
正是 `bench/recall.py` 里写下的那条坑的又一个实例。要判谁对得有一份独立于两者的金标，
目前没有，这是一个明确的未决项。

另外还有一条实际的：affinity 区间是 [0.006, 0.364]，与 ρ 完全不同的尺度。只拿它排序
不涉及标定；一旦当主分数，`ACCEPT_THRESHOLD`、交付门槛 0.5 和 `bench.recall` 的相关线
全部要重测。

### 落地形态

三级排序键 `relevance → affinity → sha256`（`pool.rank_key`）。affinity **只在打分器
给出相同分数时起作用**，不覆盖任何判断，只填补判断留下的空白；没配
`ATHENA_RERANK_MODEL` 时退化成原来的两级。

打分与 rerank 在 `_absorb` 里并发发出——两者读同一批论文、互不依赖，串行就是白等。

两条锁死"看上去做完了、实际什么也没做"的断言：reranker 真的传到了 `PaperScoutAgent`，
以及 rerank 模型真的进了检索缓存键。这条链路上已经栽过三次（边界重排器超时、重排目标
取错、打分器配置没进缓存键）。

### 真机核对：跑起来了，但暴露了一个更大的东西

同一条 query 第三次跑完整链路。

**确认在跑**：`affinity 非零 188/188`、12 次调用、0 失败——交叉编码器覆盖了整个池；
`分数取值` 回到 3 个，说明 `DEFAULT_PASSES=1` 生效。

| | 单遍+sha256 | 两遍+sha256 | 单遍+rerank |
|---|---|---|---|
| 池 | 352 | 244 | 188 |
| 边界档 | 197 | 14 | 22 |
| 打分调用 | 29 | 38 | **14** |
| 同分排序调用 | 0 | 0 | 12（失败 0） |
| scout 秒 | 631.1 | 880.6 | **936.8** |
| 建索引秒 | 66.5 | 73.2 | **3259.3** |
| 全程秒 | 1120.1 | 1495.9 | 4554.8 |
| 语料内引用边 | 0 | 8 | **17** |
| 转换 | 20/20 | 19/20 | 20/20 |

**我预测 scout 会回落到 631 秒那一档，错了——它是 936.8 秒，三轮里最高。** 但这归不到
rerank 头上：12 次调用、每次约 0.4 秒、且与打分并发发出，最多占 5 秒，不到 0.5%。同一条
query 三轮的 scout 墙钟是 631 / 881 / 937 秒，而第三轮的动作数反而最少（16 vs 23）——
**scout 内部没有分段计时，这个差异我归不了因**，只能说明它的方差比此前以为的大得多。

### 全程 4554 秒：一篇论文占了 66%

建索引 3259 秒，而语料是 20 篇 / 1654 chunk / **53362 句**（上一轮 19 篇 / 1494 chunk /
16327 句）。chunk 数差不多，句子数 3.3 倍。逐篇拆开，全在一篇上：

```
arxiv:1106.1813  SMOTE: Synthetic Minority Over-sampling Technique
  140 chunk / 35151 句 / 774904 字符    每 chunk 251 句（正常约 10）
  质量=degraded  ['tex_entrypoint_weak_inference',
                 'tex_document_environment_missing', 'rag_chunk_oversized']
```

它一篇占整个语料 66%。去掉它其余是 18211 句，与上一轮的 16327 持平。

TeX 包里没有 `egin{document}`，入口推断失败，转换器把整包连成 77 万字符。
**流水线检测到了却照样索引**：`_indexable` 只对 `suspect_empty` 一票否决，
`rag_chunk_oversized` 属于"记录但不拦"。那条策略本身是有依据的（见该函数的文档字符串：
按存在性否决整篇会误杀），但它**判的是内容对不对，不判代价**——没有任何东西限制单篇
论文能贡献多少编码量。

这不是 rerank 引入的缺陷，是它**暴露**的：SMOTE 恰恰是这个课题的奠基论文，交叉编码器
把它捞了上来，而它此前三轮都没进过交付集合。可以说它干得太好了。

### 一条必须写下来的限定

三轮交付集合的两两 Jaccard：

| | 对比 | Jaccard |
|---|---|---|
| 单遍+sha256 vs 两遍+sha256 | 交 4 / 20 | 0.114 |
| 单遍+sha256 vs 单遍+rerank | 交 4 / 20 | 0.111 |
| 两遍+sha256 vs 单遍+rerank | 交 10 / 20 | 0.345 |

**远低于离线测到的 0.69–0.79。** 原因是离线实验固定了池子、只让打分抖动，而真机三轮的
池子是 352 / 244 / 188——**检索本身的方差比打分的方差大得多**。

这不否定拆平局那项改进（在固定池子上它确实把 0.690 抬到 0.791），但它限定了这项改进在
生产里能占多大份额：**同分次序解决的是次要矛盾，主要矛盾在检索的可复现性上**，而那一
段目前没有任何常设测量。

## 六点十二、耗时到底花在哪（2026-08-18）

此前只能报到阶段级，而 scout 段内部是个黑洞：一次真机 936.8 秒，能报的只有调用次数，
**那 936.8 秒归不到任何一项**。补上分段计时之后（`--fresh-scout` 强制重跑，池 312 篇）：

| 类别 | 次数 | 忙时 | 每次 | 占 scout 墙钟 |
|---|---|---|---|---|
| **打分** | 28 | **803.0s** | 28.68s | **58.4%** |
| 后端检索 | 44 | 338.8s | 7.70s | 24.7% |
| 策略 | 6 | 110.9s | 18.49s | 8.1% |
| 同分排序 | 21 | 69.0s | 3.29s | 5.0% |
| 合计忙时 | | 1321.8s | | **96.2%** |

**没有神秘的空档**：墙钟 1374.3 秒里 96.2% 有归属，剩下 52.5 秒是提示词拼装、池排序、
artifact 落盘。

**打分是压倒性的大头。** 它占 scout 的 58.4%，而 scout 占全程的 68.6%（1374.3 / 2003.2）
——**打分一项就是整次调研的 40%**。

### 两处此前的估计是错的

- **策略调用被高估了一倍以上。** 早先按"单次约 39 秒 × 6 次 = 234 秒（25%）"估算，实测
  是 18.49 秒/次、110.9 秒、8.1%。
- **同分排序的忙时被低估了 14 倍。** 早先说"12 次 × 0.4 秒 ≤ 5 秒，不到 0.5%"，实测
  3.29 秒/次、合计 69.0 秒。离线那次 0.4 秒是 8 个请求**并发**的墙钟，不是单次耗时。

  它对**墙钟**的影响仍然接近零，而且这次能算出来：
  `打分 803.0 + 后端 338.8 + 策略 110.9 = 1252.7 秒`，与墙钟 1374.3 秒差 121.5 秒，
  而同分排序忙时 69.0 秒——说明它确实大部分藏在打分底下（`_absorb` 里两者并发）。
  **忙时和墙钟占比是两个数，不能混用**，这正是加这四个字段时就写进文档字符串的那条。

### 一条可行的优化线索（未实施）

28 次打分调用摊 312 篇 = **每次只有 11 篇**，而 `DEFAULT_BATCH_SIZE` 是 24。批次被动作
边界切碎了：每次 `_absorb` 只给自己那一批新论文打分。

而单次延迟并没有随篇数下降——文档里记的是 24 篇 23.7 秒，这里 11 篇却要 28.68 秒，说明
**每次调用有很大一块固定成本**。把打分跨动作攒批能把调用数从 28 压到约 13。

### 顺带确认的两件事

- **碎片闸门在真机命中**（上一轮）：`arxiv:1106.1813: 35151 句，平均 30 字符（低于 40），
  判为提取碎片，未入语料`，同轮其余 19 篇一篇没误伤。本轮它没触发（`shredded_papers` 为空）
  ——这一轮的池子是 312 篇，SMOTE 没进交付集合。
- **省时效果仍未验证**：上一轮 index 从 3259.3 秒降到 1.4 秒，但那主要是向量缓存命中，
  不是闸门的功劳——SMOTE 的向量在上上轮就已缓存。要量它得跑一次无缓存的。

## 七、明确没有做的

- **不重写四个 paper_* 包的划分。** 交接契约闭合、依赖注入纪律干净，这部分设计经得起看。
- **不换转换器。** 44/44、硬失败 0%，`tex_parser` 与 `pdf_parser` 是最可靠的一段。要修的
  是它*之后*没人检查结构。
- **不做 IDF 加权。** 单独看能把 MRR 抬到 0.530，但会把主题词本身是泛词的查询压成未命中。
  Phase 2 之后它的收益还会缩水。
- **真实引用图。** S2/OpenAlex 在检索阶段返回过 references，现在仍被丢掉，语料内引用边
  因此只有 16 条（每篇 0.36）。这是 Phase 3 里唯一没做完的一项——它需要把 scout 的
  references 一路传到索引，改动面比其余几项大。
- **20/44 没有真正的 abstract chunk。** 门面已经不再落在表格上，但根因在上游解析器。
