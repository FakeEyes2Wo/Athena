# 文献链路整改：从"跑得通"到"够用"

Status: current
Owner: Athena maintainers
Last verified: 2026-08-16
Source of truth: `src/athena/research/bench/`、`src/athena/research/survey/library.py`、
`src/athena/research/paper_scout/selection.py`、`src/athena/research/fork.py`

一次针对整条 Academic Survey 链路的整改，分六段落地。本文记录每一段**改了什么、为什么
是这个改法、以及用什么数字判定它做成了**。

前置阅读：[Academic Survey 全链路](academic_survey_ch.md)、
[paper_rag 真机基准](paper_rag_benchmarks_ch.md)、
[文献语料接入 loop](corpus_ideation_ch.md)。

## 零、先纠正一个前提

整改开始前的判断是"链路太脆弱、效果太差，需要重建"。实际查下来：

> `paperscout 检索 → 文献池 → 下载 TeX/PDF → 转 Markdown → 建 RAG 索引 → 暴露查询接口`
> —— 这条链路**逐段都已存在，而且就是这个顺序**。

所以整改不是重画盒子。缺陷不在盒子的划分上，在**盒子之间交付的东西没有质量契约**，而且
没有任何一个能重跑的测量在盯着。按目标形态重写一遍，最可能的结果是把同样的缺陷再造一遍。

## 一、Phase 0：把一次性测量搬进仓库

整改前，这条链路的每一个质量数字——检索 MRR、缺摘要篇数、引用边密度——都出自一次性脚本，
而**脚本不在仓库里**（`paper_rag_benchmarks_ch.md` 结尾自己写明了这点）。仓库里的
`test_paper_rag.py` 之类全用 Fake 跑，验的是代码路径不是检索质量。

后果很简单：**任何改动都无法证明变好，任何回归都不会被发现。** 所以第一件事不是改链路，
是先能量它。

`athena.research.bench` 给出三把尺子：

| 命令 | 回答的问题 | 是否需要模型 |
|---|---|---|
| `Athena-cli bench retrieval` | 改写过的提问能不能找回那篇论文 | 语义通道需要编码器 |
| `Athena-cli bench health` | 这份语料的结构够不够用 | 不需要 |
| `Athena-cli bench overlap` | 同一查询两次交付的论文重合多少 | 不需要 |

两处口径上的讲究，都是被真实数据逼出来的：

- **名次按论文算，不按 chunk 算。** 按 chunk 算会让"名额被一篇吃光"这种失败反而抬高
  分数，而那正是关键词检索真机上最严重的失效。
- **章节覆盖按全部标题层级统计**，因为 `section_search` 就是这么匹配的。只看一级标题会
  把 Ablation 报成 0/44——它几乎总是 `Experiments / Ablation Study` 这样的子节，于是这个
  数字回答的就不再是"该算子找不找得到反面证据"。

金标不在语料里的查询单独列出、**不进任何通道的分母**：那是出题问题或语料构成变化，算进
未命中就是让检索背一个不属于它的锅。这一步在真机上当场抓出过一个错标。

查询集（`bench/datasets/imbalance_auc.json`）是版本化输入数据，每条带 `rationale`——金标
改动会让前后两次基准不可比，而这种不可比是静默的，必须能在 diff 里看见。

## 二、Phase 1：语料 → 论文库

整改前每次调研都从零开始。实测一次 10 篇的调研 13 分 45 秒：

| 段 | 耗时 | 主要成本 |
|---|---|---|
| scout | 581s（71%） | 4 次策略 + 几十次打分 |
| source | 68s | HTTP，arXiv 限速 1 req/3s |
| markdown | 141s | 93 次视觉调用 |
| index | 29s | 257 批编码 |

这四段的输入**全都由内容决定**。`PaperLibrary` 按内容键把三样东西存下来，跨运行、跨项目：

- 检索结果（键：整份 `ScoutRequest` 的规范 JSON）
- 转换产物 `PaperContent`（键：paper_id + 源引用 + 转换器版本 + 视觉策略）
- 句向量（键：`PaperContent` 引用 + 编码器标识）

外加把 `LocatorCache` 落到盘上——它一直支持 JSON 持久化，只是 pipeline 从没传过 path。

### 几处必须的设计

**库和输出用两个存储。** 语料索引必须落在调用方给的那个 store 里（loop 用项目目录那份），
否则 `corpus_ref` 在宿主里解析不到——这条链路已经为这件事吃过一次亏。而缓存要跨项目共享
才有意义。命中时把索引真正要读的 blob 复制进目标 store，内容寻址让复制不改变任何 ref。

**半份内容一律判未命中。** 缺一个正文 blob 不会报错，只会建出一个检索永远返回空的语料。
向量同理：行数与句子数对不上就重新编码，绝不交出错位的矩阵。

**键里带版本。** `CONVERTER_VERSION` / `INDEX_VERSION` 改了缓存自动失效。需要人记得手动
清的缓存迟早会喂回过期结果，而那种错误只表现为"这次改动没效果"。

**检索缓存默认开，`--fresh-scout` 关。** 同一份请求是确定性输入；想要新的一批论文应当
明确说出来，而不是靠"每次都重跑"碰运气——那种"随机性"正是 Phase 2 要修的缺陷，不是特性。

验收：同一请求跑第二遍，检索 0 次、转换 0 篇、`corpus_ref` 与第一遍逐字节相同。

## 三、Phase 2：选片从散列抽签换成分面覆盖 + 边界档重排

这是整条链路唯一一处**信号被随机毁掉**的地方。

打分是四档离散的，交付名额几乎总是在某一档内部被截断。真机实测一轮：8 篇满分直接入选，
剩下 5 个名额由 **35 篇同为 0.45 的论文**争夺，胜负由 `tie_break` 的 sha256 决定——那是
刻意设计成"无偏"的，也就是刻意设计成**无信息**的。后果：同一查询两次跑测，交付的 10 篇
里只有 2 篇相同。

下游做得再对也救不回这一步。语义检索 MRR 已经很高；任务主指标是 ROC-AUC 时语料里三篇讲
AUC 的论文一次都没被引用，不是检索没找到，是选片没保证它们在。

一次模型调用做两件事：

1. **边界档重排**——只重排跨过截断线的那一档，已确定入选的不参与（它们分数本来就更高，
   重排等于用更弱的信号覆盖更强的）。调用数与档大小无关，每轮固定一次。
2. **分面覆盖**——把课题拆成若干面并标注每篇覆盖哪些面，填名额时先补没覆盖的面。
   "十篇都很贴题但全在讲同一个方法"是真实发生过的失败，而按相关性排序无法表达它。

三条边界：`max_papers=0` 在 `ScoutRequest` 里的含义是**不截断**（第一版把它读成"零篇"，
而真机默认值正好是 0）；边界档装得下时不发起调用；模型不可用/解析失败/返回空排序一律
回退散列次序——选片必须永远给得出结果。

回退理由记在 `ScoutStats.selection_note`，**不进 `errors`**：降级的选片不是失败的运行，
混进去会把真正的后端故障顶掉，也会把整轮标成 `partial`。

验收指标是 `bench overlap`。真机上拿两份既有语料试了一次：**0.080**。

## 四、Phase 3：修好语料的前门，加一条融合通道，向量走 mmap

### 门面锚点不再落在表格上

一篇论文的"落点"有三个消费者：`paper_corpus_overview` 的摘要、引用边的指向、写进 Ideator
提示词的语料目录。整改前规则是"优先 abstract kind，否则取第一个 chunk"，而 **44 篇里 20 篇
根本没有 abstract chunk**——退化之后 3 篇的门面是表格、1 篇是插图，还有几篇只有标题和作者名。

`anchor_index()` 改成：优先 abstract；否则在前 6 个里取第一个"有实质正文"的，跳过
表格/插图/公式/参考文献。"有实质正文" = 扣掉 `> Section:` 前缀、论文标题和 `\command`
形态的 LaTeX 命令之后还剩多少实词。

规则**只有一处定义**，`search` 的总览与 `bench` 的体检都 import 它。两处各写一遍的话，
体检会在规则改动后继续报旧行为——"尺子和被测对象各说各话"是最难察觉的一类错误。

真机复核（同一份语料，只换代码）：

| | 整改前 | 整改后 |
|---|---|---|
| 门面几乎无正文的篇数 | 5 | **0** |
| 锚点落在表格 / 插图 | 3 / 1 | **0 / 0** |
| 仍无真正 abstract chunk | 20 / 44 | 20 / 44（上游解析问题，未动） |

### 融合检索：先量，赢了才上

先作为 bench 的一条通道量，再决定要不要接进工具表。同一份 44 篇语料、12 条改写查询：

| 通道 | hit@1 | hit@5 | 未命中 | MRR |
|---|---|---|---|---|
| `paper_keyword_search` | 5/12 | 11/12 | 0 | 0.601 |
| `paper_semantic_search` | 9/12 | 11/12 | 1 | **0.833** |
| **`paper_search`（RRF 融合）** | 7/12 | **12/12** | **0** | 0.778 |

**融合的 MRR 比纯语义低，但它是唯一没有未命中的通道，且 hit@5 满分。** 这个取舍对本场景
是对的：Ideator 的失败从来不是"该读的论文排在第 2 而不是第 1"，而是"它根本没进视野"。
只看 MRR 会把这次交换读成退步——`compare()` 逐条比对正是为此写的。

融合按名次而不是分数：词面分是 `Σ 词频 × 关键词长度`（无上界），语义分是加权余弦（0..1），
任何线性相加都要先猜一个归一化，而那个猜测会随语料大小漂移。

### 查询向量缓存 + 向量 mmap

语义检索 96% 的时间是一次编码 API 往返，而三条 Ideator lane 拿到的是同一个任务、同一份
语料，问出来的话高度重合。缓存挂在 `CorpusCache` 上，按编码器分桶。

向量装载改走 numpy mmap，真机同一份语料实测：

| | 装载 | 峰值常驻 | 首查 | 热查 |
|---|---|---|---|---|
| 读字节 | 0.413s | 519 MB | 5.1ms | 3.5ms |
| **mmap** | **0.247s** | **367 MB** | 16.7ms | 3.8ms |

省 152 MB、装载快 1.7 倍，代价是首次查询多 11.6ms——相对那 137ms 的 API 往返可以忽略。

## 五、Phase 4：让文献到得了写代码那一步

消费端是价值流失最多的一处：语料只到得了 Ideator，而且只到一次。

**PlanAgent 拿到检索算子。** 整改前 `register_plan_agent` 的 `extra_tools` 只有 Kaggle，
于是文献只能影响"试什么"，永远影响不了"怎么实现"——而后者才是论文真正给得出细节的地方。
同时把"这条假设引了谁"拼进 plan 的 **content**（走 content 不走 `context_refs`，后者到
不了 model，这条学费已经交过）。

`corpus_tools(for_ideation=False)` 是新的默认：PlanAgent 的会话**不进**引用核验的已读
账本。默认设成不追踪，是为了让以后新增的消费方不会无声地放宽核验。

**补一轮 ideation 的触发条件改成"语料版本变了"。** `corpus_ideation_done: bool` →
`corpus_ideated_ref: str | None`。语料现在可以增量扩充，布尔标记会让扩充进来的新论文
永远读不到。旧 `state.json` 由 before-validator 迁移——`extra="forbid"` 下直接删字段会让
续跑崩掉，而不是降级。

**引用支持性判定。** 前两版核验查的都是**行为**（id 在不在语料里、本轮打开过没有）。一个
读过《数据增强综述》再拿它去支持"两两交互特征工程"的 Ideator，两版都过得去——而那正是
真机上实际发生的事。新增一层查**内容**：把被引论文里真读过的那几段交给模型，问"这段话
支持这条主张吗"。主张和干预都进提示词——只给主张，判定就退化成"这篇论文和这个话题相关吗"。

两个方向相反的保守取值：

- **单条判定**解析不出来 → 判不支持。误删一条真引用只少一份可追溯性；放行一条假引用会
  让没有根据的干预看起来有据可依。
- **整层不可用**（端点抖动）→ 保留原引用。这一层是增益，不该因为一次抖动就把已经通过
  前一关的结论清空。

## 六、Phase 5：让 A/B 第一次答得了原问题

"文献接地到底有没有用"至今**正反都没有证据**。上一次 A/B 答不了它，问题不在执行而在设计：
两臂各跑各的 PREPARE，于是各自写出一个 evaluator、各自训出一个基线。同一任务、同一数据，
两个基线的强弱就能差 0.03 以上，而 SEARCH 的改进也就 +0.05 量级——**基线方差与待测效应
同量级**。

`fork_project()` / `--fork-from` 把三样固定下来：同一个冻结 evaluator、同一个基线 commit、
同一份 artifact 存储。只让 `--survey` 不同。

```bash
Athena-cli run --project arm-off --fork-from prepared --data ...
Athena-cli run --project arm-on  --fork-from prepared --data ... --survey
```

三条不显眼但必须的规则：`corpus_ref`/`corpus_ideated_ref` 必须清空（它们正是被比较的那个
变量）；`phase` 直接落到 SEARCH（重跑 PREPARE 等于把要固定的那两样又变回变量）；目标已
存在时报错不覆盖（一条臂被另一条覆盖掉，表现出来是"分数怎么变了"，不是一条错误信息）。

## 七、明确没有做的

- **不重写四个 paper_* 包的划分。** 交接契约闭合、依赖注入纪律干净，这部分设计经得起看。
- **不换转换器。** 44/44、硬失败 0%，`tex_parser` 与 `pdf_parser` 是最可靠的一段。要修的
  是它*之后*没人检查结构。
- **不做 IDF 加权。** 单独看能把 MRR 抬到 0.530，但会把主题词本身是泛词的查询压成未命中。
  Phase 2 之后它的收益还会缩水。
- **真实引用图。** S2/OpenAlex 在检索阶段返回过 references，现在仍被丢掉，语料内引用边
  因此只有 16 条（每篇 0.36）。这是 Phase 3 里唯一没做完的一项——它需要把 scout 的
  references 一路传到索引，改动面比其余几项大。
- **20/44 没有真正的 abstract chunk。** 门面已经不再落在表格上，但根因在上游解析器。

## 八、验收数字一览

| 指标 | 整改前 | 整改后 | 出处 |
|---|---|---|---|
| 可重跑的质量测量 | 0 | 3 条命令 + 26 条用例 | Phase 0 |
| 同请求重跑成本 | 全额 | 检索 0 次、转换 0 篇 | Phase 1 |
| 门面几乎无正文的篇数 | 5 / 44 | **0 / 44** | Phase 3 |
| 锚点落在表格或插图 | 4 / 44 | **0 / 44** | Phase 3 |
| 检索未命中（最好通道） | 1 / 12 | **0 / 12** | Phase 3 |
| 语料装载峰值常驻 | 519 MB | **367 MB** | Phase 3 |
| 能查语料的 Agent | 1（Ideator） | 2（+ PlanAgent） | Phase 4 |
| 补 ideation 的次数 | 永远 1 次 | 每个语料版本 1 次 | Phase 4 |
| 引用核验层数 | 2（都查行为） | 3（+ 查内容） | Phase 4 |
| A/B 能否只变一个变量 | 否 | **是** | Phase 5 |
